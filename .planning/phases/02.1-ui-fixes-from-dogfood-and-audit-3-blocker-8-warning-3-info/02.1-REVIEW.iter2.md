## Summary

Phase 02.1 ships 3 BLOCKER + 8 WARNING + 3 INFO dogfood/audit fixes. The Rust changes (subprocess-based `claude --version` probe, relaxed `validate_course_code`, `cancel_all()` controller drain, `RelockGuard` Drop-only relock, single-source SSOT additions for `claude-version-probe`) hold up well — the capability/spawn-args/JSON triangle stays in sync, the tests pin every disposition arm, and the CSP/sanitization invariants are intact. Likewise the Svelte side respects KD-13 tokens, sanitizes message content via the existing pipeline, and the dev forwarder gate is untouched.

The review surfaces **one BLOCKER**: the W6 course-code relaxation was applied to the Rust validator only — the two frontend surfaces (`Step5AddCourse` via `onboarding-validation.ts` and `Settings → Vault` via inline regex in `VaultCategory.svelte`) still enforce the legacy `^[A-Z]{4}\d{4}$` shape, which means users **still cannot add the real-world USYD codes** the W6 fix was designed to unblock (`BIOL2010S2`, `COMP3027L`, `cs-101`, `日本語1`). The Rust tests pass but the dogfood-killer survives on the only paths users actually hit.

The warnings flag: double-submit holes in Step 6 demo import, `with_extension()` producing `foo..tmp` for extensionless files, a stale-state risk in the empty-destination guard, an inconsistent `tokio::async_runtime::block_on` on the event loop, an `imported`-state truncation that swallows multi-file selection feedback, and a `disabled` predicate divergence between the visual disable and the actual no-op guard in Step6.

The info items capture a duplicated `.ghost-link` rule, an inline `display:contents` micro-pattern footprint, an unused `dst_pre` value, and a soft naming inconsistency.

## Critical Issues

### CR-001: W6 course-code relaxation is Rust-only — both frontend validators still reject real USYD codes (dogfood-killer survives)

**File:** `src/lib/onboarding-validation.ts:28` and `src/lib/components/settings/VaultCategory.svelte:48`
**Issue:**
The W6 fix in `02.1-04` deliberately relaxed `vault_writer::validate_course_code()` from `^[A-Z]{4}\d{4}$` to a minimal path-safe validator (alphanumeric + dash + unicode, length 1..=32). The dogfood-killer documented in `UI-REVIEW.md` L150 is that real USYD codes like `BIOL2010S2`, `COMP3027L`, `cs-101`, `MATH1062` get rejected.

However, the two FRONTEND validators that gate the actual user-facing "add course" inputs are unchanged:

1. **`src/lib/onboarding-validation.ts:28`** — `Step5AddCourse` consumes `validateCourseCode()` from this file. It still tests against `const COURSE_CODE_RE = /^[A-Z]{4}\d{4}$/`.

2. **`src/lib/components/settings/VaultCategory.svelte:48`** — Settings → Vault inlines its own `const USYD_COURSE_CODE = /^[A-Z]{4}\d{4}$/` and the Add button is `disabled={validateCourseCode(courseInput).kind !== "valid"}` (L257).

Net effect: A user typing `BIOL2010S2` into either surface sees the Add CTA stay disabled / the validator say invalid. The W6 Rust-side test suite passes (because the integration test exercises the Rust function directly with sentinel `../etc`), but **no user can actually type `BIOL2010S2` and get a course folder created** because the validator gate above the IPC call never lets them through. The dogfood scenario the fix targets is still broken.

The frontmatter in `02.1-04-SUMMARY.md` claims W6 is closed — that's only true at the Rust layer.

**Fix:**
1. In `src/lib/onboarding-validation.ts`, swap the regex for the same minimal validator used in Rust:

```typescript
// Reject empty / overlong / path-separator / NUL / "." / ".." / no-alphanumeric.
const MAX_LEN = 32;
export function validateCourseCode(code: string): CodeValidation {
  const trimmed = code.trim();
  if (trimmed.length === 0) return { kind: "empty" };
  if (trimmed.length > MAX_LEN) {
    return { kind: "invalid", reason: `Too long (max ${MAX_LEN} characters).` };
  }
  if (
    trimmed.includes("/") ||
    trimmed.includes("\\") ||
    trimmed.includes("\0") ||
    trimmed === "." ||
    trimmed === ".."
  ) {
    return { kind: "invalid", reason: "Must not contain path separators." };
  }
  // Unicode-aware alphanumeric check via the `Letter` + `Number` Unicode property classes.
  if (!/[\p{L}\p{N}]/u.test(trimmed)) {
    return { kind: "invalid", reason: "Needs at least one alphanumeric character." };
  }
  return { kind: "valid" };
}
```

2. In `src/lib/components/settings/VaultCategory.svelte`, **delete** the inline `USYD_COURSE_CODE` regex + local `validateCourseCode` (L42-55) and `import { validateCourseCode } from "$lib/onboarding-validation";` at the top of `<script>`. The "Rule 3 Plan inline import substitution" comment at L18-24 explicitly says the inline is a TEMPORARY duplicate awaiting Plan 02-09 — Plan 02-09 has long landed, so the cleanup window is now.

3. Update the user-facing copy in any onboarding error path that previously said "Four letters + four digits — like `COMP3221`" to reflect the new shape (e.g. "Must be 1–32 alphanumeric characters; dashes ok").

4. Add a Vitest case to `tests/onboarding-validation*.test.ts` (or create it) asserting that `BIOL2010S2`, `COMP3027L`, `MATH1062`, `cs-101`, `日本語1` all return `{ kind: "valid" }` and that the path-poison sentinels (`../etc`, `a/b`, `\0nul`, `..`) return `{ kind: "invalid", ... }`. Mirror the Rust integration test in `src-tauri/tests/course_code_validation.rs`.

### WR-001: Step 6 demo import has no double-click guard — fast clicks fire multiple `start_import` IPCs

**File:** `src/lib/components/onboarding/Step6DemoImport.svelte:40-55`
**Issue:**
`browseFile()` is `async` but only honors `disabled={saving}` (the parent's saving flag), and the parent's `saving` is only flipped inside `next()` / `finish()` — never around Step 6's own browse-then-import flow. A user who clicks the dropzone twice in quick succession (e.g. before the OS file picker visually opens, or impatiently while a slow `start_import` runs in the background) will:

- Open two `open()` dialogs back-to-back (Tauri-plugin-dialog allows concurrent invocations on macOS).
- Issue two `start_import` IPC calls. The Rust controller will register two op_ids and process them independently.
- Race on the `imported = paths[0].split("/").pop() ?? "file"` assignment — whichever future resolves last wins the success text.

Not catastrophic (each import has its own op_id; no shared state corruption), but it surfaces in dogfood as "I clicked Browse once, why did two imports happen?" and is the same anti-pattern the parent `next()` guards against with `saving`. The bug is invisible because the OS file picker usually delays things long enough — but it WILL bite a user who double-taps the keyboard accelerator the Step 6 button hosts.

**Fix:**
Add a local in-flight flag and gate `browseFile`:

```typescript
let importing = $state(false);

async function browseFile() {
  if (importing || saving) return;
  importing = true;
  try {
    const chosen = await open({ multiple: true, directory: false });
    if (!chosen) return;
    const paths = Array.isArray(chosen) ? chosen : [chosen];
    await invoke<string>("start_import", { paths, course: null, category: "_inbox", vaultRoot });
    imported = paths.length === 1
      ? (paths[0].split("/").pop() ?? "file")
      : `${paths.length} files`;
  } catch (e) {
    console.error("[onboarding:browse-demo]", e);
  } finally {
    importing = false;
  }
}
```

Then thread `disabled={saving || importing}` onto the dropzone `<button>` (L65-71). This mirrors the `saving` discipline used by `next()` / `finish()` in `Onboarding.svelte`.

### WR-002: `atomic_write` produces `foo..tmp` for extensionless files (double-dot artifact)

**File:** `src-tauri/src/vault_writer.rs:244-260`
**Issue:**
```rust
let tmp = path.with_extension(format!(
    "{}.tmp",
    path.extension().and_then(|s| s.to_str()).unwrap_or("")
));
```

For `path = "foo"` (no extension), this calls `path.with_extension(".tmp")` which `std::path` interprets as setting the extension to the literal string `.tmp` — producing `foo..tmp` (double dot). I verified empirically:

```
"foo.pdf"  -> "foo.pdf.tmp"   ✓
"INDEX.md" -> "INDEX.md.tmp"  ✓
"foo"      -> "foo..tmp"      ✗ unexpected double-dot
```

Functionally the rename still works (the tmp file lands at the double-dot name, then gets renamed away), and `INDEX.md` always has the `.md` extension so the only real-world hit is when a user drops an extensionless file into the import flow (rare but possible — Unix dotfiles, `Makefile`, etc.). Side effects:

- Tooling that inspects mid-write tmp files sees an unusual basename.
- Cosmetic: `ls` shows `Makefile..tmp` if the rename gets interrupted, looking like garbage.

**Fix:**
Build the tmp path by string concatenation rather than `with_extension`:

```rust
fn atomic_write(path: &Path, bytes: &[u8]) -> Result<(), VaultWriterError> {
    // Append `.tmp` to the full file name (NOT via with_extension — that
    // produces `foo..tmp` on extensionless inputs).
    let mut tmp = path.to_path_buf();
    let new_name = match path.file_name().and_then(|s| s.to_str()) {
        Some(name) => format!("{name}.tmp"),
        None => return Err(VaultWriterError::IoFailed(std::io::Error::new(
            std::io::ErrorKind::InvalidInput,
            "atomic_write: path has no file name",
        ))),
    };
    tmp.set_file_name(new_name);
    // ...rest unchanged...
}
```

Then add a unit test in the `tests` module asserting the tmp name for `foo`, `foo.pdf`, and `INDEX.md`.

### WR-003: `cancel_all()` blocks the Tauri event loop via `tauri::async_runtime::block_on` — inconsistent with the BL-01 fix philosophy

**File:** `src-tauri/src/lib.rs:912-919` (CloseRequested) and `:934-941` (ExitRequested)
**Issue:**
The BL-01 fix in `kill_pgid()` (L80-94) explicitly detaches the SIGTERM→sleep→SIGKILL leg onto a worker thread to avoid blocking the Tauri event loop on Cmd+Q (avoiding the "Mneme is not responding" beach-ball). The header comment on `kill_pgid` documents the rule: "the caller returns immediately."

But the new Phase 2 `WindowEvent::CloseRequested` and `RunEvent::ExitRequested` handlers do exactly the opposite:

```rust
tauri::async_runtime::block_on(async move {
    c.cancel_all().await;
});
```

`cancel_all` itself is cheap (just flips `CancellationToken` flags under a mutex — no I/O), so in practice it returns in <1ms and the BL-01 spinning-beach-ball concern doesn't trigger. BUT:

1. The design is inconsistent — future maintainers reading the BL-01 comment "the kernel still delivers SIGKILL on the same 2s timer" will not realize `block_on` was selectively re-introduced two functions later.
2. If `cancel_all()` ever grows an `await` for a slow operation (e.g. flushing import progress to disk on shutdown, which is plausible per the comment "import tasks themselves drain their own registry entry before exiting"), the block-on becomes load-bearing for hang-on-quit.
3. `block_on` on the Tauri event loop thread is documented as a deadlock risk if any tokio task transitively tries to `tauri::AppHandle::run_on_main_thread()` while we're blocked.

**Fix:**
Either:
(a) Detach the cancel via `tauri::async_runtime::spawn` (fire-and-forget — token flips are race-free and the spawned tasks observe them on next yield):
```rust
let c = controller.inner().clone();
tauri::async_runtime::spawn(async move { c.cancel_all().await; });
app.state::<SessionRegistry>().kill_all();
```
(b) Make `cancel_all` a sync method that locks the mutex with `try_lock` + iterates (the cancellation tokens are themselves sync-cancellable via `cancel()` which doesn't await).

Add a comment that mirrors BL-01's "the caller returns immediately" so future maintainers see the constraint.

### WR-004: `Onboarding.next()` writes the entire onboarding state on Step 5 → Step 6, but `setCourses()` mutates `courses_added` in place via the live `$state` object

**File:** `src/lib/components/onboarding/Onboarding.svelte:142-145, 124-127`
**Issue:**
```typescript
function setCourses(codes: string[]) {
  onboardingState.courses_added = codes;        // mutates the live $state
}

async function next() {
  // ...
  const nextStep = Math.min(6, initialStep + 1);
  const updated = { ...onboardingState, current_step: nextStep };
  onboardingState = updated;
  await invoke("save_onboarding_state", { state: updated });
  // ...
}
```

The W3-fix replacement of `onboardingState.current_step` with `initialStep + 1` is correct. But there's a subtler stale-state risk on Step 5: `setCourses()` is invoked synchronously by `Step5AddCourse.onCoursesChange` (the chip-list mutates the underlying state). Between that synchronous mutation and the next `next()` call, no `await` boundary exists — so the `updated = { ...onboardingState, current_step: nextStep }` spread always sees the latest `courses_added`. So far so good.

The real bug: `setVaultPath()` in Step 3 calls `void next()` (L137-140), but `setVaultPath` ALSO mutates `onboardingState.vault_path` synchronously. The spread inside `next()` therefore captures the just-set path. OK.

What about a slow IPC race? After the user clicks "Use this path" in Step 3:
1. `setVaultPath(absolutePath)` is called.
2. `onboardingState.vault_path = path; void next();` — no await.
3. Inside `next()`: `if (saving || !loaded) return;` — `loaded` might still be false if the user clicks fast.
4. `next()` returns silently. The user sees nothing happen.
5. The user clicks again — by now `loaded === true` — and `next()` runs.

The vault path was already mutated in step 2, so the second click succeeds without re-clicking "Use this path." That's defensible but the `void next()` swallows the loading-state failure with no visual feedback. The CTA in `Step3VaultPicker` (L161-169) has `disabled={validation.kind !== "valid" || saving || absolutePath === ""}` — but it does NOT consult `loaded`. So the button is ENABLED, the user clicks, nothing happens, no error.

**Fix:**
Either:
(a) Surface a `loaded` prop down to each step so the CTA stays disabled until `loaded === true`.
(b) Make `next()` queue the request when `!loaded` and replay it once load resolves:

```typescript
let pendingNext = $state(false);
async function next() {
  if (saving) return;
  if (!loaded) { pendingNext = true; return; }
  // ... existing body ...
}
onMount(async () => {
  try { /* ... load ... */ } catch (e) { /* ... */ }
  loaded = true;
  if (pendingNext) { pendingNext = false; void next(); }
});
```

Either fix closes the silent-no-op on a fast Step 3 click before the load IPC resolves.

### WR-005: `Step6DemoImport.imported` swallows multi-file selection — user picks 5 PDFs, success says "Imported: lec1.pdf"

**File:** `src/lib/components/onboarding/Step6DemoImport.svelte:42-51`
**Issue:**
```typescript
const chosen = await open({ multiple: true, directory: false });
// ...
const paths = Array.isArray(chosen) ? chosen : [chosen];
await invoke<string>("start_import", { paths, /* ... */ });
imported = paths[0].split("/").pop() ?? "file";   // Only the FIRST file
```

The file picker is configured with `multiple: true`, so the user can select 5 files. The IPC happily sends all 5 to `start_import_inner` which spawns one import operation that processes all of them. But the success surface (`<p class="success">Imported: {imported}</p>`) only shows the first file's basename, hiding 4/5 of the work from the user.

In a demo step this is misleading enough that a user might think the other 4 files were lost. Worse, the user can't see the import succeeded for all of them — they'd have to dig into the recent-imports panel after onboarding.

**Fix:**
```typescript
imported = paths.length === 1
  ? (paths[0].split("/").pop() ?? "file")
  : `${paths.length} files (${paths[0].split("/").pop() ?? "first"}, …)`;
```

Better: subscribe to `getImportState().pill_state` (already a singleton) and surface the live progress + final success summary, which Step 6 currently bypasses entirely. That way "Imported: 5 of 5" appears naturally.

### WR-006: `compute_dest` falls back to `_inbox/invalid-source-basename` for empty/`.`/`..` file names — silently lumps every invalid basename into a single overwrite-prone destination

**File:** `src-tauri/src/import_controller.rs:127-152`
**Issue:**
```rust
let name_str = file_name.to_string_lossy();
if name_str.is_empty() || name_str == "." || name_str == ".." {
    return vault_root.join("_inbox").join("invalid-source-basename");
}
```

When `compute_dest` receives an unusable basename, it emits a fixed sentinel path `vault_root/_inbox/invalid-source-basename`. Two problems:

1. **Multiple bad sources collide on this path.** If a user drops two files with weird basenames in the same batch, the second one will trigger the `dest-clash:` branch — but the user-facing message ("rename your source file") is meaningless because the file doesn't have a real basename to rename to.
2. **The sentinel value `invalid-source-basename` is a magic literal**, undocumented in user-facing copy.

The comment on L138-141 says "in practice paths.iter() never produces these but the defense is cheap." Reasonable, but the defense as written is actively harmful — it lets a malformed source LAND in the vault under a confusing name instead of failing the file with a clear `error` status.

**Fix:**
Convert the sentinel into a recorded error so the file gets a `last_file_status = "error"` row in the progress stream and a structured failure in the done event:

```rust
fn compute_dest(...) -> Result<PathBuf, &'static str> {
    let name_str = file_name.to_string_lossy();
    if name_str.is_empty() || name_str == "." || name_str == ".." {
        return Err("invalid source basename");
    }
    // ... existing routing ...
    Ok(/* path */)
}
```

Caller then becomes:
```rust
let dest = match compute_dest(...) {
    Ok(p) => p,
    Err(reason) => {
        failures.push(ImportFailure {
            path: src.to_string_lossy().to_string(),
            reason: format!("invalid-name:{reason}"),
        });
        failed += 1;
        // emit progress with status "error"
        continue;
    }
};
```

And add a classifier branch to `import-error.ts` for `invalid-name:` (or let it fall through to W5-enriched fallback). Pin with a Rust unit test for the new path.

### IN-002: `.no-drag-wrap { display: contents; }` is a layout-invisible wrapper — flags accessibility tooling at minimum

**File:** `src/lib/components/TitlebarMeta.svelte:149-151`
**Issue:**
The W8 fix uses `<span class="no-drag-wrap" data-tauri-drag-region="false">` around `<ImportStatusPill />` with `display: contents` so the wrapper has no box but propagates the no-drag attribute. This works, but `display: contents` strips the element from the accessibility tree in some browser/AT combinations (a long-running WebKit + VoiceOver gotcha) — meaning the pill might lose its surrounding ancestor role context. Either pass `data-tauri-drag-region` through to `ImportStatusPill.svelte`'s root `<button>` (cleanest — eliminates the wrapper entirely), or replace `display: contents` with `display: inline-flex; align-items: center;` so the box stays accessible.

### IN-003: `move_vault` computes `dst_pre` but only checks `dst_pre != (0, 0)` — the `usize` and `u64` together still fail the same way; the tuple match obscures intent

**File:** `src-tauri/src/lib.rs:622-632`
**Issue:**
```rust
let dst_pre = if canon_dst.exists() {
    count_and_sum(&canon_dst).map_err(|e| format!("dst pre-check: {e}"))?
} else {
    (0usize, 0u64)
};
if dst_pre != (0, 0) {
    return Err(format!(
        "destination not empty: dst already contains {} file(s) totalling {} bytes — refusing to absorb pre-existing files into the migrated vault",
        dst_pre.0, dst_pre.1
    ));
}
```

The `(0, 0)` tuple match works but reads awkwardly because `count_and_sum` returns `(usize, u64)` — comparing against a `(0, 0)` literal relies on Rust's integer-literal inference selecting the right widths. It works, but `dst_pre.0 != 0 || dst_pre.1 != 0` is clearer and harder to mis-read at a glance. Also, if a future change ever has `count_and_sum` return `(0, n)` for some odd FS situation (zero entries but reported bytes), the current check correctly refuses — but the message says "contains 0 file(s) totalling N bytes" which is contradictory and confusing.

**Fix:**
Destructure and check explicitly:
```rust
let (pre_files, pre_bytes) = dst_pre;
if pre_files > 0 || pre_bytes > 0 {
    return Err(format!(
        "destination not empty: dst already contains {pre_files} file(s) totalling {pre_bytes} bytes ..."
    ));
}
```

### IN-004: `validate_inputs` accepts `category != "_inbox"` with `course == None` — silently routes to `_inbox/<filename>` (see `compute_dest`)

**File:** `src-tauri/src/import_controller.rs:169-180` + `:143-152`
**Issue:**
`validate_inputs(course, category)` checks category is in `VALID_CATEGORIES` and (if `course.is_some()`) validates the course code. It does NOT check that `category` is meaningful when `course == None`.

Result: a call like `start_import_inner(paths, course=None, category="lectures", ...)` passes validation, then `compute_dest` notices `category != "_inbox"` is true but `course.is_some()` is false → falls through the `match (course, category)` to the catch-all `_ => vault_root.join("_inbox").join(file_name)`. The file lands in `_inbox/` despite the caller saying "lectures."

Not a security issue (the regex never lies about destination — it just silently relocates), but it's a UX bug if Step 6 ever decides to pass a category other than `_inbox` for the demo. And it makes the IPC contract ambiguous: callers don't know which arm of `compute_dest` they'll hit without reading both files.

**Fix:**
Either reject the combination at `validate_inputs`:
```rust
if course.is_none() && category != "_inbox" {
    return Err(format!(
        "category {category:?} requires a course; pass course=Some(...) or use category=\"_inbox\""
    ));
}
```

…or document the silent reroute in the IPC docstring + add a Rust unit test pinning that `(course=None, category="lectures")` routes to `_inbox/`. The first option is preferable — silent reroute hides API errors.
