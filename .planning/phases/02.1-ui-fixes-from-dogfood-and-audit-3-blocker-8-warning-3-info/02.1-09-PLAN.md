<objective>
Wave 2 polish — W3 (WARNING): SettingsPanel.svelte:279-303 defines `.rail-item` + `.rail-item:hover` + `.rail-item.active` + `.rail-item.disabled` but lacks `:focus-visible`. When a user presses Tab to navigate the 8-category rail, they get the browser-default outline (typically blue or system-themed) — inconsistent with the `--orange-ring` standard used everywhere else in Phase 2 (Step1Welcome CTA L101-104, Step3VaultPicker CTA L355-357 per VaultCategory L355-357 reference, etc.).

The fix per UI-REVIEW.md L144:
```css
.rail-item:focus-visible {
  outline: none;
  box-shadow: 0 0 0 3px var(--orange-ring);
}
```

OR the alternate form per UI-SPEC §8.2 / W3 fix description in CONTEXT W3:
```css
.rail-item:focus-visible {
  outline: 2px solid var(--color-orange);
  outline-offset: 2px;
}
```

**Pick the box-shadow form** because it matches the existing pattern at Step1Welcome L101-104 and other CTAs — visual consistency wins over alternate-form flexibility.

**Why execute (not TDD):** Pure CSS-only addition; no JS behavior change; no state machine. Verification is grep + keyboard tab test (human-verify can be light because the test is "Tab through and SEE the orange ring").

**Why Wave 2:** Pure visual polish; the rail items already RESPOND to clicks; W3 closes the keyboard-accessibility gap, not a functional gap.

**Out of scope:**
- Adding focus-visible to OTHER components that lack it (DragHandle, ChatFooter buttons, etc.) — backlog. W3 specifically calls out SettingsPanel rail.
- Tab-order audit / aria-current="page" semantics — UI-SPEC §8.2 documents rail behavior; current implementation already correctly sets `aria-current` on the active rail-item per existing code review. NOT 02.1.
- Animation on focus enter/exit — KP-09 subtle = no animation on focus ring (instant feedback is the a11y default).

    STEP B — INSERT a new rule `.rail-item:focus-visible` immediately AFTER the `.rail-item:hover:not(.disabled)` rule (so the ordering is base → hover → focus-visible → active → disabled). The rule:
    ```css
    /* W3 fix (Phase 02.1 02.1-09): keyboard-navigation focus ring matches the
       --orange-ring standard used by Step1Welcome CTA (L101-104), VaultCategory CTA
       (L355-357), and all other Phase 2 interactive focus surfaces. Previously

      outline: none;

    }
    ```

    Note on ordering: CSS specificity ties between :hover, :focus-visible, .active. The visual stacking for a rail item that is simultaneously focused + active is determined by the LAST matching rule in source order, so:
    - put :focus-visible BEFORE .active so an active+focused item shows the active background + the focus ring outline (both visible).
    - If putting :focus-visible AFTER .active, an active+focused item would lose the active background to whatever :focus-visible declares — undesirable.
    - The recommended order is therefore: base → :hover → :focus-visible → .active → .disabled. Verify the executor preserves this.

    STEP C — verify .rail-item base rule does NOT already include an outline override that would defeat the new :focus-visible. If it has `outline: none;` at the base level, REMOVE that line — the new :focus-visible needs to either declare its own outline OR replace it with box-shadow (already box-shadow per our rule).
