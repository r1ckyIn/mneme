## What Was Built

### `src/lib/import-error.ts` — `extractRawTail` helper + fallback branch enrichment

**New exported pure function `extractRawTail(raw: unknown): string`** (placed AFTER `errorToString`, body-line-count = 6):

```ts
export function extractRawTail(raw: unknown): string {
    const text = errorToString(raw);
    if (!text) return "";
    const lastColon = text.lastIndexOf(":");
    if (lastColon === -1) return "";
    const tail = text.slice(lastColon + 1).trim();
    return tail;
}
```

- Reuses the existing private `errorToString` helper for string / Error / object normalization.
- `lastIndexOf(":")` returns -1 for colon-free input → empty tail → no enrichment downstream.
- `slice(lastColon + 1).trim()` strips leading whitespace from the segment (errors typically formatted as `"prefix: detail"` with a single space after the colon).

**Modified `classifyImportError` fallback branch**. The structured-branch order (`isDestClashShape` first, `isPermissionDeniedShape` second) is preserved verbatim. The final return changed from `return GENERIC_IMPORT_ERROR_MESSAGE` to:

```ts
const tail = extractRawTail(raw);
if (tail.length === 0) {
    return GENERIC_IMPORT_ERROR_MESSAGE;
}
return `${GENERIC_IMPORT_ERROR_MESSAGE} (details: ${tail})`;
```

- JSDoc on `classifyImportError` updated with a new bullet documenting the W5 fallback enrichment contract.
- Inline comment block at the new branch cites Phase 02.1 plan 02.1-05 + dogfood #8 origin.

**No new imports added** — the helper composes existing internals.

## Edge Cases Verified

The `extractRawTail` helper handles the spectrum of inputs documented in the plan's success criteria:

| Input shape | `extractRawTail()` returns | `classifyImportError()` returns |
|-------------|----------------------------|-------------------------------|
| `null` / `undefined` | `""` (errorToString empty) | bare GENERIC |
| `""` (empty string) | `""` (no text) | bare GENERIC |
| `"no colon here"` | `""` (lastIndexOf = -1) | bare GENERIC |
| `"prefix: detail"` | `"detail"` (single colon) | GENERIC + `(details: detail)` |
| `"a: b: c: d"` | `"d"` (last colon wins) | GENERIC + `(details: d)` |
| `"  : leading-colon-detail  "` | `"leading-colon-detail"` (trim) | GENERIC + `(details: leading-colon-detail)` |
| `"trailing-colon:"` | `""` (slice after `:` is empty after trim) | bare GENERIC |
| `Error("io: detail")` | `"detail"` (Error.message normalized) | GENERIC + `(details: detail)` |
| `{ message: "x: y" }` | normalized via JSON.stringify of object, last colon split | GENERIC + `(details: "y"})` |

The `{ message }` case demonstrates that the helper degrades gracefully on object payloads — the JSON serialization may produce a less-tidy tail, but it never throws and the headline is always preserved. The Test 4 case (`new Error("io error: permission denied")`) is consumed by the permission-denied classifier BEFORE reaching the fallback, so the user sees the structured `DUPLICATE_PERMISSION_DENIED_MESSAGE` rather than `(details: permission denied)`.

## Deviations from Plan

### [Rule 3 — Test contract conflict] source-clash regression assertion updated

**Found during:** Task 1 verification step (running `tests/import-error-classifier.test.ts` after applying the W5 fix).

**Issue:** A pre-existing assertion in `tests/import-error-classifier.test.ts` L118-128 pinned `classifyImportError("source-clash:/vault/_source/lec.pdf")` to return the bare `GENERIC_IMPORT_ERROR_MESSAGE`. With the W5 enrichment branch now active, that input returns the enriched form `"Something went wrong while importing. Check the console for details, or try again. (details: /vault/_source/lec.pdf)"` because:
1. `source-clash:` is NOT matched by `isDestClashShape` (which looks for `dest-clash:` — distinct prefixes for distinct error semantics).
2. `source-clash:` is NOT matched by `isPermissionDeniedShape` (no `permission denied` / `eacces` / `os error 13` substrings).
3. So the input falls through to the now-enriched fallback branch.

The test FAILED post-W5-fix with: `Expected: "Something went wrong..." Received: "Something went wrong... (details: /vault/_source/lec.pdf)"`.

**Fix:** Updated the assertion (NOT the source code). The test's documented intent — captured in the test's prose comments — was `"no silent claim that source-clash: routes anywhere specific"`. The W5 contract preserves that intent: `source-clash:` is still NOT a classifier branch (no special-case routing); it flows through the SAME fallback that any other colon-containing unmatched input flows through. The new assertions explicitly verify:
1. Headline starts with `"Something went wrong while importing."` (W5 contract).
2. Tail ends with `(details: /vault/_source/lec.pdf)` (W5 enrichment applied uniformly).
3. Result is NOT `DEST_CLASH_MESSAGE` and NOT `DUPLICATE_PERMISSION_DENIED_MESSAGE` (proves no special-case classifier branch consumed it — same contract the original `.toBe(GENERIC_IMPORT_ERROR_MESSAGE)` was trying to enforce, now expressed in W5-aware terms).

**Why this is Rule 3 not Rule 4:** This is a test alignment, not an architectural change. The plan's `must_haves.truths` explicitly says "Existing classifier branches (dest-clash / permission-denied) are UNAFFECTED — they return their structured copy BEFORE the fallback enrichment runs" — and they ARE unaffected. The pre-existing test was asserting a too-specific consequence (bare GENERIC) of the pre-W5 fallback, not a classifier-branch invariant. No user decision was needed; the plan's W5 contract directly determines the new expected behavior for ALL unmatched colon-containing inputs.

**Why this is NOT Rule 1 (bug):** The W5 enrichment is the EXPECTED, plan-mandated behavior. The source code is correct. The test was pinning a pre-W5 implementation detail (no enrichment) rather than the test's actual documented intent (no special-case routing). Updating the assertion to match both the implementation AND the documented intent is the correct fix.
