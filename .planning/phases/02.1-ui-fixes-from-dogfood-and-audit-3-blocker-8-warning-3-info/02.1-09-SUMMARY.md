## W3 Root Cause

`SettingsPanel.svelte` L279-303 defines four rail-item CSS rules:

1. `.rail-item` (base — neutral, transparent border-left, `--color-warm-dark-soft` text)
2. `.rail-item:hover:not(.disabled)` (cream-deep background on hover)
3. `.rail-item.active` (cream-deep background + orange border-left + warm-dark text)
4. `.rail-item.disabled` (opacity 0.7)

There was no `:focus-visible` rule. When a user pressed Tab to navigate the 8-category rail, the browser fell back to its default focus outline — on macOS WKWebView (the Tauri webview) this is typically a system-themed blue ring, sometimes black on cream backgrounds. The result is visually inconsistent with everything else in Phase 2:

- Step1Welcome CTA (`onboarding/Step1Welcome.svelte` L101-104) uses `outline: none; box-shadow: 0 0 0 3px var(--orange-ring);`
- Step3VaultPicker CTA (`onboarding/Step3VaultPicker.svelte` L255-258) mirrors the same pattern.
- VaultCategory CTA (per plan reference) uses the identical token.

Keyboard users on the Settings panel got a focus indicator that broke the visual brand — small but visible inconsistency, flagged by UI-REVIEW.md L142-144 as a WARNING.

---

## Fix Shape

A single 11-line CSS block (1 multi-line disposition comment + a 4-line rule) inserted between the existing hover and active rules. Verbatim addition:

```css
/* W3 fix (Phase 02.1 02.1-09): keyboard-navigation focus ring matches the
   --orange-ring standard used by Step1Welcome CTA (L101-104), VaultCategory CTA
   (L355-357), and all other Phase 2 interactive focus surfaces. Previously
   rail items rendered the browser-default outline (system-themed; visually
   inconsistent). Ordering note: kept BEFORE .active so an active+focused
   rail-item still shows the active background — visual stacking is determined
   by source order at equal specificity. Closes UI-REVIEW.md L142-144. */
.rail-item:focus-visible {
  outline: none;
  box-shadow: 0 0 0 3px var(--orange-ring);
}
```

Nothing else changed in the file.

---

## CSS Ordering Rationale

Source order at equal specificity matters when two rules both apply to the same element. A rail item that is both `.active` and `:focus-visible` is a real combination (Tab to the currently-selected category). The rule order in the final file is:

```
L279  .rail-item                       (base)
L293  .rail-item:hover:not(.disabled)  (hover)
L303  .rail-item:focus-visible         (focus — NEW)
L307  .rail-item.active                (active)
L312  .rail-item.disabled              (disabled)
```

- `.rail-item.active` declares `background`, `border-left-color`, `color` — none of which `.rail-item:focus-visible` re-declares.
- `.rail-item:focus-visible` declares `outline` and `box-shadow` — neither of which `.rail-item.active` touches.

So in practice the two rules are property-disjoint: an active+focused rail-item gets both the orange-border + cream-deep + warm-dark text (from `.active`) AND the orange box-shadow ring (from `:focus-visible`). Both are visible. Either source order would render the same — but the plan recommended hover → focus → active as a natural state-progression read order, and the disposition comment documents this choice so a future maintainer reading the file top-to-bottom understands the intent.
