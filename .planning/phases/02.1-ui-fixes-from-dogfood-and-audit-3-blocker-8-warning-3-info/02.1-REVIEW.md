### WR-007 fix (the iter 2 work) is sound

The merge formula in `Onboarding.svelte:117-125`:

```typescript
onboardingState.current_step = initialStep;
onboardingState.vault_path =
  onboardingState.vault_path || loadedState.vault_path;
onboardingState.courses_added =
  onboardingState.courses_added.length > 0
    ? onboardingState.courses_added
    : loadedState.courses_added;
onboardingState.completed_at =
  loadedState.completed_at ?? onboardingState.completed_at;
```

walked through each field for the four merge configurations (live empty / live populated × loaded empty / loaded populated):

**`vault_path` (live-wins falsy coalesce):**
- live="" + loaded="" → "" (cold first launch — correct, validator gates CTA on Step 3)
- live="/path" + loaded="" → "/path" (the race the fix is for — preserved)
- live="" + loaded="/old" → "/old" (cold resume — correct)
- live="/new" + loaded="/old" → "/new" (live wins — correct)
- **Edge case "empty string as legitimate user value"**: Impossible. `setVaultPath` is invoked only from `Step3VaultPicker.confirm()` (line 105-123) which carries `if (validation.kind !== "valid" || saving || absolutePath === "") return;` — a literal "" can never reach `setVaultPath`. The `||` falsy coalesce is safe by construction. Verified in source at Step3VaultPicker.svelte:109.

**`courses_added` (live-wins-when-non-empty ternary):**
- live=[] + loaded=[] → [] (correct)
- live=["X"] + loaded=[] → ["X"] (chip add during first-launch race — preserved)
- live=[] + loaded=["X"] → ["X"] (cold resume — correct)
- live=["X"] + loaded=["Y"] → ["X"] (live wins)
- **Asymmetric edge case noted as IN-007 below**: user CLEARING their last chip back to `[]` mid-race would let the loaded prior courses re-populate. Practical impact is tiny (rare race window on resume + mild UX cost of re-clearing) — not a regression risk.

**`completed_at` (loaded-wins nullish coalesce):**
- Frontend NEVER mutates this field directly — only the Rust `complete_onboarding` IPC sets it via `finish()` which navigates to "/" immediately. So `onboardingState.completed_at` cannot acquire a stale non-null value mid-race. The `??` direction is correct: a loaded non-null timestamp wins over a live null.

**`current_step` (URL wins, unchanged from earlier WR-03 fix):**
- Preserved. No regression.

### IN-007: `tests/onboarding-resume.test.ts` lacks a symmetric "user CLEARS courses_added mid-race" test for the WR-007 ternary

**File:** `tests/onboarding-resume.test.ts:290-312`
**Issue:**
The WR-007 merge formula at `Onboarding.svelte:120-123` is asymmetric — `onboardingState.courses_added.length > 0` preserves any non-empty live array but lets a loaded non-empty array re-populate an empty live array. The current test "WR-007 merge: in-flight courses_added (Step 5 chip click) survives a load with empty courses" exercises only the "live populated wins" direction. The inverse — user CLEARS the last chip during the load window, then load resolves with prior courses — silently re-adds the prior courses to the live state.

Trace of the race:
1. T+0ms — `onMount` starts; user is on Step 5 with `courses_added = ["COMP3221"]` already loaded from disk in a prior session.
2. T+5ms — User clicks the X on the last chip; `removeCourse` mutates `onboardingState.courses_added = []`.
3. T+30ms — `load_onboarding_state` resolves with the still-on-disk `courses_added = ["COMP3221"]`.
4. T+30ms — Merge fires: `live.length === 0` → loaded wins → `onboardingState.courses_added = ["COMP3221"]`. The user's clear is silently undone.

Practical bounds:
- The race window is narrow on a fast SSD — sub-50ms — and onMount happens once per page load. The window only exists for users who navigate INTO a step with pre-existing chip data and remove chips before the IPC resolves.
- Worst-case observable consequence: the user clicks X, sees the chip vanish, then sees it reappear ~30ms later. They re-click X. Annoying, not data-destructive (no persistence happens unless they click Continue).
- `~/.mneme/onboarding.json` is NOT silently corrupted in this scenario because no `save_onboarding_state` fires from the chip removal — it only fires on `next()`.

This is the inverse of WR-007's primary race (vault_path live-wins). Both branches of the live-vs-loaded ternary should have a symmetric pin so a future inversion of the comparison operator (`.length === 0 ? live : loaded`) would visibly break the suite.

**Fix (optional, low priority):**

Add to `tests/onboarding-resume.test.ts` describe block 3:

```typescript
test("WR-007 merge (asymmetric edge): user clears courses_added to [] during load — loaded prior courses re-populate (acknowledged asymmetry)", () => {
  const onboardingState: OBState = {
    current_step: 1,
    vault_path: "/already/picked",
    courses_added: ["COMP3221"],  // initial state from a prior session
    completed_at: null,
  };

  // User clicks X on the last chip BEFORE the load resolves.
  onboardingState.courses_added = [];

  // Load resolves with the on-disk prior courses.
  const loadedState: OBState = {
    current_step: 5,
    vault_path: "/already/picked",
    courses_added: ["COMP3221"],
    completed_at: null,
  };

  applyMerge(onboardingState, loadedState, /* initialStep */ 5);

  // Asymmetric: loaded wins when live is empty. Documents the contract.
  expect(onboardingState.courses_added).toEqual(["COMP3221"]);
});
```

The test serves as both a regression pin AND inline documentation that the asymmetry is deliberate (matches the existing WR-007 comment block at Onboarding.svelte:120-123 which the test author already wrote in plain text but did not encode as an assertion).

**Why INFO, not WARNING:** No live bug. The asymmetry is acknowledged in the source comment. The race window is sub-50ms and the consequence is a re-click, not data corruption. The risk is regression-without-test if someone inverts the operator during a future refactor.
