## Warnings

### WR-007: WR-004 `pendingNext` replay races with `onMount`'s full-state REPLACE — user mutations on Step 3 can be silently overwritten

**File:** `src/lib/components/onboarding/Onboarding.svelte:107` + `:97-126` + `:162-165`
**Issue:**
The iter 1 WR-004 fix added a `pendingNext` queue so a fast `next()` click pre-mount is replayed once `loaded === true`. The replay site is:

```typescript
onMount(async () => {
    try {
      const loadedState = await invoke<OnboardingState>("load_onboarding_state");
      onboardingState = { ...loadedState, current_step: initialStep };   // ← REPLACES
    } catch (e) { ... }
    loaded = true;
    if (pendingNext) {
      pendingNext = false;
      void next();                                                       // ← REPLAY
    }
});
```

The replacement at line 107 wipes out any in-place mutations made between IPC start and resolution. Combined with `setVaultPath` (line 162-165):

```typescript
function setVaultPath(path: string) {
  onboardingState.vault_path = path;   // ← mutates in place
  void next();
}
```

…the following race produces silent data loss into `~/.mneme/onboarding.json`:

1. T+0ms — `onMount` calls `load_onboarding_state` (pending).
2. T+5ms — User clicks Step 3 "Use this path" while load is still resolving. Step 3's `confirm()` runs `vault_create_scaffold` + `save_config` (writes config.json successfully).
3. T+20ms — `setVaultPath("/Users/qy/StudyVault")` mutates `onboardingState.vault_path` in place.
4. T+20ms — `next()` runs, sees `!loaded`, sets `pendingNext = true; return`.
5. T+30ms — `load_onboarding_state` resolves with the fresh-install default `{ vault_path: "" }`.
6. T+30ms — `onboardingState = { ...loadedState, current_step: 3 }` REPLACES the object. The user's `vault_path = "/Users/qy/StudyVault"` is **clobbered to `""`**.
7. T+30ms — `if (pendingNext)` fires `next()`. The spread `{ ...onboardingState, current_step: nextStep }` now reads `vault_path: ""` from the just-overwritten state.
8. T+30ms — `save_onboarding_state` persists `{ vault_path: "", current_step: 4, ... }` to `~/.mneme/onboarding.json`.

Observable consequences:
- The wizard advances to Step 4, but `onboardingState.vault_path === ""` from here on. Step 5's `addCourse()` early-returns with "Vault path not set — go back to Step 3." Confusing but recoverable.
- `~/.mneme/onboarding.json` is now permanently corrupted. On next app launch the layout reads `vault_path: ""` from onboarding.json and treats the wizard as in-progress with no vault path. The user has to re-pick.
- `config.json` is correct (Step 3's `save_config` ran successfully), so subsequent sessions that read config.json work — but the onboarding-state divergence is a latent bug.

The race window is small on a fast SSD (sub-50ms) but real on a slower disk (NFS-mounted home, encrypted FileVault, cold cache, large config). The previous "silent return" behavior preserved the user's mutation in `onboardingState`; the queue-replay fix introduces the corruption window without a defense.

The new test `tests/onboarding-resume.test.ts` only asserts source-grep regex pins (line 125-167) — it does NOT exercise the runtime race, so this regression would not surface in CI.

**Fix (pick one):**

Option A — Re-merge user-mutated fields when replaying the queued next() so the loaded-state values do NOT clobber subsequent in-place mutations:

```typescript
onMount(async () => {
    let loadedSnapshot: OnboardingState | null = null;
    try {
      loadedSnapshot = await invoke<OnboardingState>("load_onboarding_state");
    } catch (e) { console.error("[onboarding:load]", e); }
    if (loadedSnapshot) {
      // Preserve in-place mutations that happened while we were awaiting.
      onboardingState = {
        ...loadedSnapshot,
        current_step: initialStep,
        vault_path: onboardingState.vault_path || loadedSnapshot.vault_path,
        courses_added: onboardingState.courses_added.length > 0
          ? onboardingState.courses_added
          : loadedSnapshot.courses_added,
      };
    }
    loaded = true;
    if (pendingNext) { pendingNext = false; void next(); }
});
```

Option B (cleaner UX) — Thread `loaded` as a prop through each step child and OR it into the existing `disabled={... || !loaded}` predicates. Pair with a small "Loading…" affordance on Step 3 / Step 5 so the user sees why their click is gated. Requires touching every step component but eliminates the silent click.

Option C — Make `setVaultPath` / `setCourses` await `loaded` before mutating. Simplest but introduces an inconsistency where the child appears to advance while the parent still waits.

Option A is the smallest patch; Option B is the most correct.

Add a runtime test that simulates the race: mock `load_onboarding_state` with a delayed promise, mutate `onboardingState.vault_path` synchronously, fire `next()`, await the load, assert the saved state includes the user's vault_path. The existing `tests/onboarding-resume.test.ts` "WR-03 fix — Onboarding.svelte source-file invariants" block is regex-only and would not catch this.

## Info

### IN-005: WR-003 `tauri::async_runtime::spawn(cancel_all)` may not flip cancellation tokens before process exit; inline rationale comment overstates the guarantee

**File:** `src-tauri/src/lib.rs:923-931` (CloseRequested) and `:951-958` (ExitRequested)
**Issue:**
The iter 1 WR-003 fix replaced `tauri::async_runtime::block_on(cancel_all())` with a fire-and-forget `tauri::async_runtime::spawn(async move { c.cancel_all().await })`. The comment claims:

> WR-003 fix (Phase 02.1 02.1-REVIEW): detach cancel_all via tauri::async_runtime::spawn so the caller returns immediately and the Tauri event loop is never blocked — mirrors the BL-01 discipline established in kill_pgid (lines 80-94). The token flips inside cancel_all are themselves race-free; spawned tasks observe them on their next yield.

Two precision issues:

1. **The kernel-SIGKILL timer analogy does not transfer.** The cited "kernel still delivers SIGKILL on the same 2s timer" line in `kill_pgid` is a property of `std::thread::spawn` (a real OS thread, not subject to runtime teardown). `tauri::async_runtime::spawn` schedules a future on a tokio executor that **is** subject to runtime teardown. On `RunEvent::ExitRequested`, the tokio runtime is teardown-eligible — the spawned future may never run before the process dies.

2. **`cancel_all` is not strictly race-free.** It acquires `registry.lock().await` before iterating. Under contention with a concurrent `start_import_inner` holding the same mutex, the spawned cancel_all blocks on the lock. On Cmd+Q with active imports, this is unlikely to matter (the import loop holds the mutex very briefly), but the comment's wording overstates the safety property.

**Practical impact:** Zero in the normal Cmd+Q path. The OS reaps every thread / file descriptor / tokio task as part of process termination. The cancellation tokens not firing means individual import tasks don't get to emit their `cancelled` progress event — but they were never going to write those events to disk anyway (events go through Tauri IPC which is also dead).

**Why INFO, not WARNING:** No observable user-facing or data-loss consequence. The fix achieves its stated goal of not blocking the event loop. The concern is purely the misleading comment + the loss of the previous "I have actually flipped every cancellation token before returning" guarantee that the old `block_on` provided synchronously.

**Fix (optional, low priority):**

Either (a) tighten the comment to drop the SIGKILL analogy and acknowledge that on `RunEvent::ExitRequested` the spawned cancel_all is best-effort and may not run; or (b) provide a sync iterator over the registry (try_lock + iterate `cancel_token.cancel()`, which is itself sync) and call it without `async_runtime::block_on` or `spawn`:

```rust
pub fn cancel_all_sync(&self) {
    if let Ok(reg) = self.registry.try_lock() {
        for (_, op) in reg.iter() { op.cancel_token.cancel(); }
    }
    // try_lock failure on shutdown is acceptable — kernel reaps tasks anyway.
}
```

Then `WindowEvent::CloseRequested` and `RunEvent::ExitRequested` can call `controller.cancel_all_sync()` synchronously without involving the async runtime. This is the cleanest mirror of BL-01's discipline (no event-loop block + no race with runtime teardown).

### IN-006: WR-006's new `invalid-name:<reason>` failure prefix has no frontend classifier regression test

**File:** `src/lib/import-error.ts` (consumer of the new prefix) + `tests/import-error-classifier.test.ts` (missing pin)
**Issue:**
The WR-006 fix added a new failure prefix `invalid-name:<reason>` (e.g., `invalid-name:invalid source basename`) to the per-file failure stream and `ImportDoneEvent.failures[].reason`. The fix's comment in `import_controller.rs:259-264` claims:

> `import-error.ts can fall through to the W5-enriched fallback for invalid-name:` — see classifyImportError.

Manual verification confirms the claim works: `classifyImportError("invalid-name:invalid source basename")` returns `"Something went wrong while importing. (details: invalid source basename)"` via the W5 last-colon-tail enrichment. But:

- No test in `tests/import-error-classifier.test.ts` or `tests/import-error-fallback.test.ts` asserts this behavior. A future refactor that re-orders the classifier branches (e.g., adding an explicit `invalid-name:` arm above `dest-clash:`, or changing the prefix delimiter) could change the surfaced message without any test failing.
- The Rust integration test path for `start_import_inner` with an unusable basename is genuinely hard to exercise (`std::fs::write` rejects empty basenames), so the inline comment in `import_controller.rs:803-819` documents that the contract is pinned via the direct `compute_dest_rejects_unusable_basenames` unit test plus trust in the in-line branch's straight match-Err-record-continue shape. Reasonable Rust-side; the frontend half of the contract is untested.

**Why INFO:** No live bug — the W5 fallback works today. The risk is regression-without-test if someone later adds an explicit classifier branch or changes the prefix shape. Low likelihood, low blast radius (worst case is a slightly less friendly error message).

**Fix:** Add to `tests/import-error-classifier.test.ts` (mirrors the existing `source-clash` regression test at L118-142):

```typescript
test("REGRESSION: invalid-name: prefix falls through to W5-enriched generic message (WR-006 contract)", () => {
    const result = classifyImportError("invalid-name:invalid source basename");
    expect(result).toMatch(/^Something went wrong while importing\./);
    expect(result).toMatch(/\(details: invalid source basename\)$/);
    expect(result).not.toBe(DEST_CLASH_MESSAGE);
    expect(result).not.toBe(DUPLICATE_PERMISSION_DENIED_MESSAGE);
});
```

This pins the message shape that import_controller's inline comment promises.
