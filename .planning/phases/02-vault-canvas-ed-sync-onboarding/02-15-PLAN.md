Gap closure plan — Hardening cluster (Wave 1, parallel-safe with 02-13).

Closes 4 WARNINGs from 02-REVIEW.md whose root causes are isolated to 4 disjoint files (no overlap with 02-13 / 02-14 / each other):

1. WR-02 (vault_writer.rs L319-337) — with_temporary_writable_permission runs an explicit chmod 0o444 AFTER the user closure succeeds; if that chmod fails the `?` returns early WITHOUT calling guard.disarm(). The Drop guard then re-runs set_permissions(..., 0o444) hitting the same failure mode. The relock-then-relock sequence is wasted work, and the contract gets fragile. Fix: disarm BEFORE the explicit chmod, then rely on Drop as the relock authority unconditionally. Net effect: ONE set_permissions call regardless of success/failure. WR-02 also calls out documentation: the comment block at L271-281 must explicitly state "Drop is the relock authority."

2. WR-03 (Onboarding.svelte L90-104) — next() reads onboardingState.current_step which is bound to initialStep via $effect. On slow systems the user could click Continue between (a) URL-prop change triggering $effect and (b) the $effect actually mutating state. The save then writes a stale step. Risk small but persists silently to JSON. Fix: compute nextStep from initialStep (URL truth) directly. Defense-in-depth: add a `loaded` gate that flips after onMount's async load resolves; next() refuses to fire until loaded.

3. WR-06 (audit-capabilities.sh L151-156) — import_handle() whitelist regex `(vault_writer|import_controller|lib)\.rs$` matches any file ending in `lib.rs` (e.g. `my_lib.rs`, `evil_lib.rs`, `tauri_lib.rs`). A future contributor (or malicious actor) could accidentally inherit the whitelist by naming a file `<x>_lib.rs`. Fix: anchor with a `/` slash prefix → `/(vault_writer|import_controller|lib)\.rs$` so only the literal whitelist matches, not arbitrary file suffixes. Defense-in-depth: alternate stricter form anchoring from `src-tauri/src/` repo root is documented but not chosen (fragile if file location ever moves).

4. WR-11 (Step5AddCourse.svelte L39-62) — addCourse invokes course_create with `root: vaultRoot` where vaultRoot flows from Onboarding's state. If the user reaches Step 5 via direct URL (/onboarding/5) without completing Step 3, vaultRoot is "" (empty). The Rust handler then resolves `Path::new("").join("courses").join(code)` to `courses/COMP3221` (relative to cwd). In dev cwd is the project root; in production cwd may be `/` or `/Applications`. Fix: frontend guard at Step5AddCourse.addCourse + defense-in-depth Rust guard in vault_writer::create_course rejecting empty/whitespace root.
