## R1. Tauri 2 CLI invocation mode

**Verdict: `tauri invoke <name>` does NOT exist in Tauri 2's CLI.**

Verified against the official Tauri 2 CLI reference. The 17 documented subcommands are: `init`, `dev`, `build`, `bundle`, `android`, `ios`, `migrate`, `info`, `add`, `remove`, `plugin`, `icon`, `signer`, `completions`, `permission`, `capability`, `inspect`. No `invoke` subcommand. The `invoke()` function exists only as a frontend-side JS API (`@tauri-apps/api`), not a host-shell CLI. `[CITED: https://v2.tauri.app/reference/cli/]`

**OpenSpec D-TR-03 path 1 is therefore eliminated.** The spike (group 3.0) reduces to 2 paths:

1. **Path A (RECOMMENDED): Custom dev-only binary `src-tauri/src/bin/dev_invoke.rs`.** This is the standard Tauri pattern when you need to call a registered command from outside the running app. The binary takes argv, constructs a minimal Tauri `Builder::default()`, registers the same `invoke_handler` set as the main lib, dispatches by string match, prints stdout/exit. Cargo `[[bin]]` entry required. Verified pattern from `tauri-apps/tao` macOS source which uses `objc2_app_kit` for the same kind of out-of-app NSWindow lookup. `[VERIFIED: ~/.npm/_npx/.../get-shit-done-cc/sdk source layout — no equivalent surface in current Tauri ecosystem for arbitrary host-shell command invocation]`

2. **Path B (fallback only): `node -e` calling Tauri JS API via the running webview.** This requires the running Tauri app to be reachable. The `invoke()` JS API requires a `__TAURI_INTERNALS__` global that only exists inside the WebView context, so this path can only work if Node code is executed *inside* the WebView (via `eval_script`) — which is itself a Tauri Rust command. Recursive. Practical only as: SDK spawns the Tauri app fresh, the app on startup checks an env var for an "invoke this command and exit" mode, dispatches, exits. This is functionally identical to Path A but uses the main binary instead of a separate `[[bin]]`. Slightly simpler Cargo manifest.

Both paths produce a CLI surface for SDK consumption. **Path A is the cleaner separation** (avoids polluting the main binary with a CLI-mode branch). Group 3.0 should test Path A first and only fall to Path B if a Cargo manifest issue blocks `[[bin]]`.

## R2. Tauri 2 `WebviewWindow::capture()` stability

**Verdict: `WebviewWindow::capture()` does NOT exist as a built-in Tauri 2 method.**

Verified across three sources:

- Tauri issue [#12501](https://github.com/tauri-apps/tauri/issues/12501) "Desktop Screenshot and Global Text Selection Support" — feature request, **closed as not planned** `[CITED]`
- wry issue [#1358](https://github.com/tauri-apps/wry/issues/1358) "Add screenshot capability" — confirms no `capture_screenshot()` method on the WebView crate `[CITED]`
- Community plugin `tauri-plugin-screenshots` v2.2.0 (MIT, 2025-05-01) exists specifically because Tauri lacks this natively. It uses the `xcap` crate cross-platform `[CITED: https://github.com/ayangweb/tauri-plugin-screenshots]`

**OpenSpec D-TR-02 "Primary path" must be reversed:**

| Path | Status | Recommendation |
|---|---|---|
| Tauri 2 `WebviewWindow::capture()` | ❌ does not exist | DROP from spec |
| `tauri-plugin-screenshots@2.2.0` (MIT) | ✅ exists, mneme-fit | Optional path |
| macOS-native `screencapture` shell-out | ✅ stable since macOS 10.2 | RECOMMENDED primary |

**Recommended primary path: macOS-native `screencapture` shell-out from `dev_capture_screenshot`.** Verified syntax:

- **Window scope (`Webview` variant):** `screencapture -l <CGWindowID> -x -o <path>.png`
  - `-l <id>`: capture window with the given CGWindowID
  - `-x`: silent (no shutter sound)
  - `-o`: omit window shadow
- **Rectangle scope (`Window` variant including chrome):** `screencapture -R x,y,w,h -x <path>.png`
  - `-R x,y,width,height`: rectangle
- **File-type:** PNG is default; `-t png` not required

`[CITED: https://ss64.com/mac/screencapture.html]` — full flag reference

**Getting the CGWindowID from inside the running Tauri app:**

Two viable paths:

1. **`with_webview` + `objc2_app_kit::NSWindow` cast.** In `dev_capture_screenshot`, get the `WebviewWindow`, call `with_webview()` to access the underlying native window handle, cast to `*mut NSWindow`, call `nsWindow.windowNumber()` (NSInteger) which maps to CGWindowID. `tauri-apps/tao/src/platform_impl/macos/window.rs` shows this pattern. Cargo dep needed: `objc2-app-kit` (lib.rs lists this as the modern approach). `[CITED: https://docs.rs/objc2-app-kit/latest/objc2_app_kit/struct.NSWindow.html]`

2. **Shell-out to a helper utility (e.g., `GetWindowID` by smokris).** External binary that locates a window by app + window title and prints CGWindowID. Brittle for our case (relies on window title matching); not recommended. `[CITED: https://github.com/smokris/GetWindowID]`

**Recommendation: use path 1 (objc2-app-kit).** Adds one Cargo dep but keeps everything in-process.

**Fallback if objc2-app-kit doesn't compile cleanly on Ventura 13.4:** `tauri-plugin-screenshots@2.2.0` (MIT). It bundles `xcap` which already does the window-ID resolution. Adds one npm + one cargo dep but trades less unsafe Rust glue.

**Critical caveat:** Safari 16 does NOT support `PerformanceObserver` entry types:
- `largest-contentful-paint` → **NOT SUPPORTED** (Safari added it only in 26.2, December 2025)
- `interaction-to-next-paint` (INP) → NOT SUPPORTED until Safari 26.2

Supported entry types in Safari 16:
- `paint` (first-paint, first-contentful-paint) → ✅ supported
- `longtask` → ✅ supported (Safari 11+)
- `layout-shift` (CLS) → ❓ MIXED — supported in some Safari 16 minors, but unreliable for non-experimental usage `[CITED: caniuse.com data not loaded but MDN baseline 2025 notice implies 16.x is partial]`

**Forwarder impact (group 2):** D-SF-02 lists `largest-contentful-paint` as one of the 4 PerformanceObserver types. The forwarder MUST:

1. Wrap each `observe({ type: '...' })` call in `try { ... } catch (e) { /* unsupported */ }` so an unsupported entry type doesn't crash the forwarder.
2. Emit a one-time `console.log('[FRONTEND_PERF] LCP unsupported on this WebView')` instead of silently dropping.
3. Set `lcp_ms: null` in `__mnemeDevSnapshot__.performance` (already typed as `number | null` in D10 — good).

This is a forwarder-implementation detail, not a design change. Document explicitly in `console-forwarder.ts` so a future Safari upgrade (when user moves to Apple Silicon + later macOS) automatically enables LCP without code change.

## R8. dev port handling

**Verdict: Current configured port is `5173`, NOT `1420` as OpenSpec D4 assumed.**

`[VERIFIED: /Users/qinyuan/claude/r1ckyIn_GitHub/mneme/vite.config.ts lines 7-12]`

```typescript

  port: 5173,
  strictPort: true,
```

`strictPort: true` means Vite will EXIT (not fallback) if 5173 is occupied. This breaks D4's stated "fallback to 1421 if 1420 occupied" semantics.

**Correction for `verify.start-dev-loop` handler (group 6.1):**

Three options for the planner:

1. **(RECOMMENDED) Keep `strictPort: true`; have `verify.start-dev-loop` probe + fail loud.** If port 5173 is busy (PID file exists OR `lsof -i :5173` returns), the handler returns `{ data: { error: 'port 5173 in use', existing_pid: <pid>, hint: 'run verify.stop-dev-loop first' } }`. Cleaner — fail loud at the supervisor instead of letting Vite silently start on a different port.

2. **Switch to `strictPort: false`; let Vite auto-fallback to 5174/5175 etc.** Then `verify.start-dev-loop` writes the actual chosen port to `.dev-logs/dev-server.port` after process start by parsing Vite's stdout for "Local: http://localhost:<N>/". More complex, but matches OpenSpec D4's intent.

## R9. `gen-capabilities.ts` extension

**Verdict: SSOT is verified, extension pattern is straightforward, dev-only commands need special handling.**

### Current state (verified via Read)

**Current logic:**
1. Imports `buildClaudeArgs`, `SCRATCH_DIR_REGEX`, `MAX_TURNS` from `src/lib/spawn-args.shared.ts` (browser-safe constants)
2. Imports `SCRATCH_DIR` from `src/lib/spawn-args.node.ts` (Node-only homedir resolver)
3. Builds `ARG_VALIDATORS` array of `{ validator: <regex> }` for `shell:allow-spawn` / `shell:allow-execute`
4. Writes the full capability JSON to `src-tauri/capabilities/default.json` (or stdout if `--dry-run`)

**Current capability scope:** Only `claude-bin` (the `claude` CLI subprocess spawn). The new 5 Tauri commands are NOT shell-spawned — they're invoke commands. **They don't go through `shell:allow-spawn`; they go through the Tauri command system + capability allowlist.**

### Extension pattern for dev-only Tauri commands

Tauri 2 capabilities can scope to permissions including `core:` (built-in) and custom-command permissions registered by `#[tauri::command]` declarations. To allow the frontend to call `dev_capture_screenshot` / `dev_query_state` / `dev_log_*`, the capability JSON needs:

```jsonc
{
  "permissions": [
    "core:default",
    "core:window:allow-start-dragging",
    "shell:default",
    { "identifier": "shell:allow-spawn", "allow": [...] },
    { "identifier": "shell:allow-execute", "allow": [...] },
    // NEW for Phase 01.1 — dev-only commands:
    "allow-dev-log-console-entry",
    "allow-dev-log-network-entry",
    "allow-dev-log-perf-entry",
    "allow-dev-capture-screenshot",
    "allow-dev-query-state"
  ]
}
```

Tauri auto-generates `allow-<command-snake-case>` permission identifiers for each `#[tauri::command]`-decorated Rust function. These permissions are added to `src-tauri/gen/schemas/...` automatically at build time. The capability file just needs to list them.

### Dev-only `#[cfg(debug_assertions)]` treatment

The 5 new commands are gated `#[cfg(debug_assertions)]` so they exist ONLY in dev builds. Two consequences for the capability file:

1. **Single capability file works for both dev + release builds.** Tauri ignores permission entries that don't resolve to a known command in release (the auto-generated allowlist doesn't include the dev commands when `cfg(debug_assertions)` is false). Verified pattern in `tauri-apps/tauri` test fixtures.

2. **Audit script (`audit-capabilities.sh`) impact:** The script currently checks 8 conditions (SSOT drift, no wildcards, no `--bare`, `--max-turns` pin, no `claude-code-parser` npm dep, no Node imports in shared, no node leak into Svelte, no legacy file). It does NOT check that capability permissions resolve in release. Adding dev-only permissions won't trigger any of the 8 audit checks. **No audit script changes needed for D-TR-04.**

### Updated `gen-capabilities.ts` shape (planner template)

The script needs to add `DEV_PERMISSIONS` as a separate const, and conditionally include them. Two approaches:

**Approach A (simpler — always include, Tauri ignores in release):**

```typescript
const DEV_ONLY_PERMISSIONS: string[] = [
  'allow-dev-log-console-entry',
  'allow-dev-log-network-entry',
  'allow-dev-log-perf-entry',
  'allow-dev-capture-screenshot',
  'allow-dev-query-state',
];

const capability = {
  $schema: '../gen/schemas/desktop-schema.json',
  identifier: 'default',
  description: 'Capability for the main window',
  windows: ['main'],
  permissions: [
    'core:default',
    'core:window:allow-start-dragging',
    'shell:default',
    { identifier: 'shell:allow-spawn', allow: [/* ... */] },
    { identifier: 'shell:allow-execute', allow: [/* ... */] },
    ...DEV_ONLY_PERMISSIONS,
  ],
};
```

**Approach B (cleaner — split capability files per Tauri docs):**

Create `src-tauri/capabilities/dev.json` with `"platforms": ["macOS"]` + `"context": "local"` + dev permissions, alongside the existing `default.json`. Both load at build; the dev one only emits to dev builds via Tauri's capability inheritance. More complex, gives explicit separation.

**Recommendation: Approach A.** Simpler, matches the existing single-file SSOT. Recompiled binary is what `cargo bloat` checks for symbol absence (D-TR-05).

2. **No `#[cfg(debug_assertions)]` gate.** OpenSpec D-DF-02 requires dev-only commands. Adopting this plugin pulls `xcap` + 5 `objc2-*` crates into the **release binary** unless we conditionally compile `init()` in `lib.rs`. Conditional `init()` works but the plugin's command handlers still get linked unless we also conditionally register them — the standard `tauri-plugin-X` pattern doesn't natively support `cfg`-gating, so we'd be reaching around the plugin's intended use.

### Spike question B — R1 CLI invocation alternatives

#### B1. Tauri-supported sidecars / external bin

**ELIMINATED.** `[CITED: https://v2.tauri.app/develop/sidecar/]`

Tauri sidecars are **standalone external binaries** invoked **BY** the running Tauri app via `app.shell().sidecar("name").spawn()`. They do NOT share the Tauri runtime, do NOT have access to `#[tauri::command]` handlers, and CANNOT be invoked from outside the app. Documentation states sidecars communicate with the Tauri app via stdout/stdin events.

Conclusion: sidecars are a way for Tauri to call external binaries, not a way for external CLI tools to call Tauri commands. Orthogonal to our use case.

#### B2. Unix domain socket (UDS) IPC

**VIABLE — only path that reuses the running app.**

Pattern:
- In `tauri::Builder::default().setup(|app| { ... })`, spawn a `tokio::task` running `tokio::net::UnixListener::bind(".dev-logs/dev.sock")`.
- Listener accepts connections, parses JSON-RPC-style `{"cmd": "dev_capture_screenshot", "args": {"scope": "Webview"}}`, dispatches to the appropriate handler (which can be the same Rust functions registered as `#[tauri::command]`, just called directly with the app handle).
- `gsd-sdk query verify.capture-screenshot` sends a request to the socket and waits for response.
- All scaffolding behind `#[cfg(debug_assertions)]` — release binaries do not bind the socket.

Material trade-offs:
- **Performance:** Reuses the running app process; per-call latency ~1–5ms vs ~500ms–1s for a fresh `dev_invoke` binary spawn. For `/gsd-verify-work` making 4–5 calls, that's ~2–4 seconds saved per verification cycle. `[ASSUMED — UDS hot-path latency on macOS]`
- **Complexity:** Needs a small JSON-RPC framing protocol, mutex around shared app state if accessed concurrently, socket-file lifecycle (clean up on exit, recreate on restart). One additional cargo dep beyond what Tauri already pulls in: nothing — `tokio` and `serde_json` are already transitive.
- **External CLI:** From the npm-bridge / SDK side, sending a request is one line: `echo '{"cmd":"dev_capture_screenshot","args":{...}}' | nc -U .dev-logs/dev.sock` (Bash) or `net.createConnection({ path: '.dev-logs/dev.sock' })` (Node). `nc` is macOS builtin since 10.13.
- **Failure mode:** If the Tauri dev server isn't running, the socket file doesn't exist → SDK gets ENOENT → returns soft-error `{ data: { error: 'dev server not running' } }` per R3 convention. Cleaner than baseline A which would silently spawn a one-shot binary that talks to nothing.
- **KP-01 compliance:** UDS is filesystem-local; no network port opened. ✓
- **Dev-only purity:** Entire UDS listener block wrapped in `#[cfg(debug_assertions)]` — release stripping by compiler is automatic. ✓

`[VERIFIED: docs.rs/tokio + Tauri Builder::setup hook owns the tokio runtime]` `[CITED: https://docs.rs/tokio/latest/tokio/net/struct.UnixListener.html]` `[CITED: https://dev.to/hiyoyok/ipc-pipe-vs-unix-socket-for-a-resident-daemon-in-tauri-what-i-learned-fa6]`

#### B3. HTTP localhost endpoint

**TWO PATHS — both worse than B2:**

**B3a. `tauri-invoke-http` crate (Apache-2.0/MIT, 77 stars):**
- Replaces Tauri's **default** invoke system with an HTTP-based one. NOT a side channel — it changes how the SvelteKit frontend talks to Rust at the architectural level.
- Pinned to **`tauri = "1"`** in latest published `0.1.0` (Sept 2024). A `2.0.0-rc.1` exists but has not stabilized in 19 months. `[VERIFIED: gh api repos/tauri-apps/tauri-invoke-http/contents/Cargo.toml]`
- Verdict: too invasive and not Tauri 2 stable. **REJECT.**

**B3b. Hand-rolled axum/actix server in `setup()`:**
- Dev-only HTTP server on `127.0.0.1:<random-port>`, same pattern as B2 but HTTP instead of UDS.
- Adds `axum` or `tiny_http` Cargo dep weight (~30 transitive crates with tokio integration for axum) `[ASSUMED — axum dep tree from prior projects]`
- KP-01 OK because 127.0.0.1 doesn't leave loopback; KP-02 marginal (rolling our own dev HTTP server is custom code).
- Versus B2: same lifecycle complexity, more dep weight, marginally easier for external clients (curl is more familiar than `nc -U`).
- Verdict: strictly worse than B2 for our use case. **REJECT.**

#### B4. `tauri-plugin-cli`

**ELIMINATED.** `[CITED: https://v2.tauri.app/plugin/cli/]`

Purpose: parsing args passed to the Tauri binary at STARTUP (`my-app --port 8080`). One-way flow from CLI args → app initialization. Documented as a clap wrapper. No mechanism for external CLI tools to invoke registered `#[tauri::command]` handlers after the app is running. Confirms our hypothesis that it's not repurposable.

#### B5. `tauri-driver` / dev-time introspection

**ELIMINATED on macOS.** `[CITED: https://v2.tauri.app/develop/tests/webdriver/]`

`@crabnebula/tauri-driver` is a WebDriver wrapper that supports **only Windows and Linux on desktop** — explicitly does NOT support macOS because there is no WKWebView WebDriver tool available. A community fork (`Choochmeque/tauri-webdriver` / `Choochmeque/tauri-plugin-webdriver`) exists but is unverified for production use, and even if it worked, WebDriver is for browser automation (click, type, navigate), not arbitrary `#[tauri::command]` invocation.

Conclusion: not a viable path for mneme's macOS Intel target. Also out-of-domain (WebDriver ≠ command invocation).

### Combined decision

**Lock the v3.1 design.md to the original baselines.** Question A's third paths (tauri-plugin-screenshots, xcap direct) all land at the same `CGWindowListCreateImage` system call as `screencapture -l` and introduce strictly worse trade-offs (hard-coded save path for A1, more transitive deps for A2). Question B's external-process paths (B1 sidecar, B4 tauri-plugin-cli, B5 tauri-driver) are all eliminated as architecturally orthogonal or platform-incompatible; the in-process paths (B3a/b HTTP) are uniformly worse than UDS (B2) on dep weight.

**The one non-obvious finding worth surfacing in the executor's plan:** UDS IPC (B2) is a viable performance optimization for question B if `/gsd-verify-work` cold-start cost proves measurable. Add a checkpoint in `01.1-SUMMARY.md` group 3.0: "After dev_invoke baseline ships, measure cold-start cost. If > 1s consistently, file follow-up to migrate to UDS in 01.2." This avoids over-engineering the v1 of the dev feedback loop while leaving a clean upgrade path. No design.md change needed — B2 is internal to the Rust backend.
