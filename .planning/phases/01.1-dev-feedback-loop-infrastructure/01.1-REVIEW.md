# Phase 01.1: Code Review Report

**Reviewed:** 2026-05-12
**Depth:** deep (cross-file analysis, log format contract tracing, regex correctness verification)
**Files Reviewed:** 14

## Summary

Phase 01.1 delivers solid dev-feedback-loop infrastructure. The Svelte forwarder is well-guarded for production stripping, the Rust dev commands are correctly triple-gated, the `#[cfg(debug_assertions)]` stripping is empirically verified via `nm`, and the unsafe NSWindow block is properly scoped with a correct SAFETY comment. The log-rotation, debounce, and D-SF-04 IO-error swallow logic are sound. The `format_console_entry` / `format_network_entry` formatters are clean and unit-tested.

Two HIGH bugs were found through cross-file log-format contract tracing:

1. The `gsd-dev-snapshot.mjs` regex cannot match the actual `console.log` line format produced by `format_console_entry`, making `dev_query_state` (via the CLI path) always time out.
2. The `dev_invoke.rs` CLI handler for `dev_query_state` writes a `snapshot.request` stub file, but the running Tauri app contains no polling loop to pick it up — the two halves of the protocol never connect.

Together these mean the `npm run gsd-dev-snapshot` path is broken end-to-end. The direct in-app `dev_query_state` Tauri command (triggered from inside the running app) works correctly; only the CLI bridge path is affected.

## High Issues

### HG-01: Snapshot regex fails against actual `console.log` line format

**File:** `scripts/gsd-dev-snapshot.mjs:105`

**Issue:** The regex used to extract the snapshot JSON from the log file tail is:

```
/\[snapshot\](\{[\s\S]*?\})\s*(?:$|\n)/gm
```

This requires the JSON block `{...}` to be followed immediately by optional whitespace and then end-of-line. However, `format_console_entry` in `dev.rs` formats all console entries as:

```
[FRONTEND_CONSOLE]<TAG>|<ts>|<message>|<source_str>\n
```

The snapshot Tauri JS snippet sends `message = "[snapshot]" + jsonString` with no source, so the log line becomes:

```
[FRONTEND_CONSOLE]SNAPSHOT|<ts>|[snapshot]{...json...}|\n
```

After the closing `}` of the JSON comes `|` (the empty source field delimiter), not `\s*` and end-of-line. The regex therefore never matches. Verified with Node:

```javascript
const line = '[FRONTEND_CONSOLE]SNAPSHOT|2026-05-12T10:00:00Z|[snapshot]{"url":"http://localhost","viewport":{"w":1280}}|\n';
const matches = [...line.matchAll(/\[snapshot\](\{[\s\S]*?\})\s*(?:$|\n)/gm)];
// matches.length === 0  <-- BUG
```

**Fix:** Change the regex to also accept `|` as a valid terminator after the JSON:

```javascript
// Option A: minimal fix — include | as a valid terminator
const matches = [...tail.matchAll(/\[snapshot\](\{[\s\S]*?\})(?:\||\s*(?:$|\n))/gm)];

// Option B: parse the FRONTEND_CONSOLE line with parseConsoleLine, extract the
// message field, then strip the "[snapshot]" prefix — aligns with the actual format.
```

### HG-02: `snapshot.request` file is written by CLI but never polled by the running app

**File:** `src-tauri/src/bin/dev_invoke.rs:62-76` (writer); `src-tauri/src/dev.rs` (poll loop absent)

**Issue:** When `dev-invoke dev_query_state` is called from the CLI, `dev_invoke.rs` writes `.dev-logs/snapshot.request` containing `"1"` and returns a hint string. The comments in `gsd-dev-snapshot.mjs` and `.dev-logs/README.md` state that "the running Tauri app polls `.dev-logs/snapshot.request`". However, no poll loop exists anywhere in the running Tauri app. A full-text search of `src-tauri/src/` confirms zero references to `snapshot.request` other than the write site in `dev_invoke.rs`.

The in-app `dev_query_state` Tauri command (called by `window.__TAURI_INTERNALS__.invoke('dev_query_state', ...)`) works correctly via `WebviewWindow::script_injection`. But the CLI bridge path — which `gsd-dev-snapshot.mjs` uses — writes a file that nothing reads. The script waits `deadlineMs` (default 3 000 ms) for a `[snapshot]` line that never appears, then exits non-zero.

**Fix (interim):** Return an explicit error from `dev_invoke.rs` instead of silently writing the stub file:

```rust
"dev_query_state" => {
    Err("dev_query_state via CLI is not implemented in v1 — \
         invoke from inside the running Tauri app. \
         Phase 01.2 UDS IPC will replace this stub.".to_string())
}
```

This surfaces the failure immediately rather than making the caller spin for 3 seconds.

**Fix (full):** Phase 01.2 UDS upgrade per RESEARCH spike B2. Alternatively, implement a file-poll loop in `lib.rs` startup that watches for `snapshot.request` and triggers `dev_query_state` via the webview window handle. This requires the app to have a background tokio task watching the file, which is feasible but adds complexity.

## Warnings

### WR-01: Pipe characters in log messages are silently truncated by `parseConsoleLine`

**File:** `scripts/gsd-dev-scan-logs.mjs:79-102`

**Issue:** `parseConsoleLine` splits the log line on `|` to extract `tag | ts | message | source`. The format produced by `format_console_entry` is:

```
[FRONTEND_CONSOLE]TAG|ts|message|source:line\n
```

Pipe characters in the logged message content are embedded unescaped — `argsToString` in the forwarder calls `JSON.stringify` (which does not escape `|`) and `format_console_entry` uses Rust string interpolation with no escaping. When `parseConsoleLine` splits on `|`, any pipe in the message terminates the message field early. For example, `console.log("status: ok|error")` produces message `"status: ok"` with source `"error"` in the scan output — silently wrong.

**Fix:** Escape `|` in message content before writing to the log, or use a delimiter that cannot appear in JS log output. Minimal fix in `format_console_entry`:

```rust
let safe_message = message.replace('|', "<PIPE>");
format!("[FRONTEND_CONSOLE]{tag_str}|{ts}|{safe_message}|{source_str}\n")
```

Mirror the unescaping in `parseConsoleLine`. A cleaner fix is to use `\x1e` (ASCII Record Separator) as the field delimiter, which cannot appear in normal log output.

### WR-02: XHR reuse causes duplicate entries in `network.log`

**File:** `src/lib/dev/console-forwarder.ts:287`

**Issue:** `patchedSend` attaches a `loadend` listener via `this.addEventListener('loadend', callback)`. If the same `XMLHttpRequest` object is reused (`.open()` + `.send()` called again on the same instance), a second `loadend` listener is attached. When the second request completes, both listeners fire, producing two `network.log` entries for one network round-trip. The XHR spec permits reuse; some polling patterns rely on it.

**Fix:** Add `{ once: true }` to self-remove the listener after it fires:

```typescript
this.addEventListener("loadend", () => {
  const end = typeof performance !== "undefined" ? performance.now() : Date.now();
  logNetwork(trace.method, trace.url, this.status, end - trace.start);
}, { once: true });
```

### WR-04: `__TAURI_INTERNALS__` internal bridge API used in injected script

**File:** `src-tauri/src/dev.rs:457`

**Issue:** The injected snippet in `dev_query_state` calls `window.__TAURI_INTERNALS__.invoke(...)`. `__TAURI_INTERNALS__` is Tauri's private internal bridge, not the documented stable API. If a future Tauri patch renames or restructures this object, the script injection silently fails — `WebviewWindow::script_injection` returns `Ok(())` but the injected code throws a TypeError, which the injected try/catch catches and logs as `[snapshot-error]`. The failure mode is invisible to the Rust command caller.

The caller (`gsd-dev-snapshot.mjs`) would wait `deadlineMs` and time out without a specific indication that the Tauri internal API changed.

**Fix (short-term):** In the injected error path, include a hint about the likely cause:

```rust
"  } catch (e) {",
"    window.__TAURI_INTERNALS__.invoke('dev_log_console_entry',",
"      { level: 'error', message: '[snapshot-error]bridge-unavailable: ' + String(e), tag: 'snapshot' });",
"  }",
```

**Fix (proper):** Phase 01.2 UDS IPC upgrade. Track `__TAURI_INTERNALS__` as a Tauri version pinning dependency.

### IN-01: `tokio` is in `[dependencies]` but only used in `#[cfg(debug_assertions)]` code

**File:** `src-tauri/Cargo.toml:23`

**Issue:** `tokio` with 8 features is declared under `[dependencies]` (compiled into release builds). All tokio usage is in `dev.rs` which is `#[cfg(debug_assertions)]`-gated, meaning tokio is a release-build dependency whose code is never reached in release. Tauri likely pulls tokio transitively, but the explicit 8-feature entry in `[dependencies]` may add to compile time and binary size unnecessarily.

**Fix:** Move to a conditional dependency using a dev-loop Cargo feature:

```toml
[features]
default = []
dev-invoke = []
dev-loop = ["dep:tokio"]

[dependencies]
tokio = { version = "1", features = ["sync", "rt", "rt-multi-thread", "macros", "process", "time", "fs", "io-util"], optional = true }
```

Or use `[target.'cfg(debug_assertions)'.dependencies]`. This is low-priority if Tauri already links tokio transitively.

### IN-02: Test fixture uses trailing `|` not produced by the actual writer

**File:** `scripts/__tests__/gsd-dev-scan-logs.test.mjs:53-56`

**Issue:** Test fixtures write lines like:

```
'[FRONTEND_CONSOLE]ERROR|2026-05-11T23:00:00Z|too-old|x.ts:1|'
```

The trailing `|` after the source field is not produced by `format_console_entry` in `dev.rs`, which generates `tag|ts|message|source\n` with no trailing pipe. The tests pass because `parseConsoleLine` handles 5-part splits gracefully (the empty 5th part is unused). But the fixtures do not match the actual wire format. If the format changes, these tests would not detect the divergence.

**Fix:** Remove the trailing `|` from test fixtures to match the exact output of `format_console_entry`:

```javascript
// Before (wrong format):
'[FRONTEND_CONSOLE]ERROR|2026-05-11T23:00:00Z|too-old|x.ts:1|'

// After (matches actual writer):
'[FRONTEND_CONSOLE]ERROR|2026-05-11T23:00:00Z|too-old|x.ts:1'
```

### IN-03: `entry.duration` term in LCP calculation is a no-op per the W3C spec

**File:** `src/lib/dev/console-forwarder.ts:326`

**Issue:**

```typescript
perfState.lcp_ms = entry.startTime + (entry.duration || 0);
```

For `LargestContentfulPaint` entries, `entry.duration` is always `0` per the W3C LCP spec — only `startTime` carries the meaningful LCP render time. The `+ (entry.duration || 0)` term is always a no-op but implies the author believed `duration` contributed. The code is functionally correct but misleading.

**Fix:**

```typescript
perfState.lcp_ms = entry.startTime;
```
