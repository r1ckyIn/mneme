## Decisions Made

- **screencapture shell-out as primary** (E1 errata, R2): `WebviewWindow::capture()` doesn't exist in Tauri 2 (issue #12501 closed as not planned), so the `screencapture -l <CGWindowID>` (webview) / `-R <x,y,w,h>` (window) path is the only viable approach. macOS-native binary at hard-coded `/usr/sbin/screencapture` path (SIP-protected; T-01.1-06-04 mitigation).
- **objc2-app-kit windowNumber over osascript** (R2 path 1): in-process call from `dev_capture_screenshot` against the same process's Tauri WebviewWindow handle. `windowNumber()` is a const method returning NSInteger by value — minimal `unsafe` surface, no borrow leakage.
- **dev_query_state via webview script injection + log-pipe** (D10 v1): synchronous round-trip via Tauri's pending-eval-with-callback API would require WRY's callback path (Tauri 2.2+); the conservative v1 implementation pipes the JSON through dev_log_console_entry with tag `snapshot`. Phase 01.2 UDS upgrade tracked.
- **Triple-gating for dev surfaces**: (1) `#[cfg(debug_assertions)]` on file/module, (2) `[[bin]] required-features = ['dev-invoke']`, (3) lib.rs invoke_handler split between debug/release branches. Defense in depth — release binary cannot reach the dev surface even if `cfg(debug_assertions)` were somehow inverted.
- **Atomic-commit boundary rebalance** (deviation 2 below): the plan prescribed 3 commits (1=Cargo.toml+formatters, 2=writer task + commands, 3=binary + caps + release-verify). Because commit 1 and commit 2 both touch the same file in overlapping ways (dev.rs needed to be split mid-content for the plan's literal sequence), I rebalanced to: commit 1 = full dev.rs + Cargo + lib.rs (Tasks 1+2+3+4), commit 2 = integration tests only (Task 3 RED+GREEN), commit 3 = binary + caps + release-verify (Tasks 5+6+7). Each commit is independently revertable, which is the original intent of the atomic-boundary rule.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] R9 Approach A capability registration is unsatisfiable in Tauri 2.11.1**

- **Found during:** Task 6 — initial `node --experimental-strip-types scripts/gen-capabilities.ts` + `cargo build` cycle.
- **Issue:** The plan author's R9 Approach A premise — "Tauri auto-generates `allow-<command-snake-case>` permission identifiers for each `#[tauri::command]`-decorated Rust function" — is empirically false. Tauri 2.11.1 only resolves permission identifiers that originate from a `tauri-plugin` crate's manifest (e.g. `tauri-plugin-shell` defines `shell:allow-spawn`). For raw `#[tauri::command]` functions registered via `generate_handler!`, there is no permission identifier — the registration itself is the IPC permission. Adding `allow-dev-capture-screenshot` to capability JSON makes the Tauri build fail with: `Permission allow-dev-capture-screenshot not found, expected one of <core+plugin permissions>`. The plan's `must_have` truth that `default.json contains: "allow-dev-capture-screenshot"` is unsatisfiable.
- **Fix:** Kept the `DEV_ONLY_PERMISSIONS` array in `scripts/gen-capabilities.ts` as a documentation anchor with a 30-line rationale block explaining the finding, but commented out the spread `...DEV_ONLY_PERMISSIONS` into the capability permissions array. `src-tauri/capabilities/default.json` is identical to its pre-plan state. PATTERNS.md L376-394 had already flagged this verification as open ("Verify: do dev_* commands need an explicit capability entry, or does the cfg(debug_assertions) gate suffice for prod hiding?") — the empirical answer is: capability entries are unnecessary.
- **Threat impact:** zero. The dev commands are already triple-gated: `#[cfg(debug_assertions)]` on file, `[[bin]] required-features = ['dev-invoke']`, and the lib.rs `generate_handler!` cfg-split between debug/release branches. The release binary genuinely lacks the symbols (D-TR-05 verified via `nm`).
- **Files modified:** `scripts/gen-capabilities.ts` (commented spread + rationale block).
- **Verification:** `bash scripts/audit-capabilities.sh` → `[audit] PASS`. `cargo build --release` → `Finished release profile`. `nm target/release/mneme | grep dev_` → zero matches.
- **Committed in:** `4506dcb`.

### Plan-prescribed atomic-commit boundary rebalanced

**2. [Rule 1 - Scope] Plan's 3-commit boundary mid-file-splitting was impractical**

- **Found during:** Task 8 (commit phase) — reviewing the plan's prescribed commit boundaries against the actual file diff.
- **Issue:** The plan prescribed commit 1 = Cargo.toml + formatters (lines ~1-300 of dev.rs) + 3 unit tests, and commit 2 = writer task + 5 commands + 3 integration tests + lib.rs wiring (lines ~300-540 of dev.rs + new integration test file + lib.rs builder split). Because both commits touch dev.rs in overlapping ways, satisfying the literal sequence would require: write only formatters → commit → append writer task + commands → commit. This is wasteful for parallel work and produces a commit-1 state where the lib.rs builder is partially split (referencing types not yet in dev.rs). Each commit must be independently revertable; the plan's literal sequence is not.
- **Fix:** Rebalanced to a logically-grouped 3-commit boundary that preserves independent revertability:
  - Commit 1 (`0652298`): full Cargo.toml + full dev.rs (formatters + writer + commands) + lib.rs builder split + 7 unit tests
  - Commit 2 (`afedb13`): the integration test file ONLY (separately revertable)
  - Commit 3 (`4506dcb`): dev_invoke binary + gen-capabilities.ts Rule-1 deviation + release-verify
- **Verification:** Each commit is independently revertable (commit 2's tests would just disappear; commit 3's binary + caps would disappear without breaking the lib.rs surface). The plan's intent — "3 atomic commits, no SSOT drift between commits" — is preserved.

### Cargo `[[bin]]` required-features feature flag — first-of-its-kind in mneme

- The plan flagged this as convention-establishing (PATTERNS.md L225-246). No deviation; documented for the record. The `[[bin]] name="dev-invoke" path="src/bin/dev_invoke.rs" required-features=["dev-invoke"]` block + `[features] dev-invoke = []` is the first `[[bin]]` entry in `src-tauri/Cargo.toml`. ### `tauri::generate_handler!` cfg-split idiom — workaround documented

- The macro does NOT accept `#[cfg]` between handler entries. Workaround: split `tauri::Builder::default()` chain into a debug branch (`#[cfg(debug_assertions)] let builder = builder.manage(DevWriter::new(...)).invoke_handler(generate_handler![...8 commands...]);`) and a release branch (`#[cfg(not(debug_assertions))] let builder = builder.invoke_handler(generate_handler![...3 commands...]);`). Setup + window-event + run-event hooks remain shared. Documented in `src-tauri/src/lib.rs` comment block.

### objc2-app-kit + Tauri ns_window() interop — clean

- No rough edges. `WebviewWindow::ns_window()` (Tauri 2.11.1) returns `Result<*mut std::ffi::c_void, tauri::Error>`. Cast to `*mut NSWindow` (from `objc2_app_kit::NSWindow`), `unsafe { (*ns_ptr).windowNumber() }` returns `isize` (NSInteger on macOS = `i64`). Single `unsafe` block with explicit SAFETY comment covering the invariants: (1) pointer is valid for the WebviewWindow lifetime, (2) we hold the `&WebviewWindow` borrow for the call duration, (3) `windowNumber()` is a const method returning by value with no further borrow leakage.
