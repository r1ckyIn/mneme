<domain>
## Phase Boundary

Land the **cross-repo dev feedback loop** that eliminates Claude asking the user for terminal output / console logs / screenshots / DOM state during UI work. Phase 01.1 is **infrastructure**, not product — it changes the contract for how `/gsd-execute-phase` and `/gsd-verify-work` interact with the user across all r1ckyIn projects (mneme first, dogfood subject).

Two halves ship together:

- **mneme-side (Tier D + E)** — full-spectrum dev-only Svelte forwarder + five dev-only Tauri Rust commands + npm-script bridge + `.dev-logs/` scaffold. Project-specific capability exposure.
- **GSD upstream (Tier A + B + C live at `~/.claude/get-shit-done/`)** — three patches to `workflows/verify-work.md` + eight new `verify.*` SDK handlers + one shared `templates/visual-review.html`. The rule layer that makes the mneme-side capability meaningful, designed to feed a future upstream PR to `gsd-build/get-shit-done`.

Delivery threshold:

1. `/gsd-verify-work 01.1` runs against the patched workflow + freshly built mneme capability — the patched workflow self-validates against the very phase that patches it (bootstrapping done early in execute order, per OpenSpec tasks.md "Execution order rationale").
2. `automated_ui_verification` detects mneme's npm-script bridge → Tauri branch runs → `verify.scan-signals` returns structured issue list → `verify.render-review-html` produces a single 4-bucket HTML at `.planning/handoff/<date>-phase-01.1-verify.html` → `verify.validate-html` passes → user receives one HTML path, replies once.
3. **Execute-phase silence** is observable: no Summary block, no Visual Review HTML, no console-asking / log-pasting / DOM-inspecting questions surface during execute. All verification surfaces only at the phase-end gate.

This phase is **cross-cutting workflow infrastructure**, not a ROADMAP-business phase mapping to a v1+v1.x REQ. It introduces a NEW capability `dev-feedback-loop` (see `openspec/changes/automate-dev-feedback-loop/specs/dev-feedback-loop/spec.md`).

### Svelte forwarder (D3 OpenSpec)

- **D-SF-01 Single file at `src/lib/dev/console-forwarder.ts`** + companion `src/lib/dev/snapshot-selectors.ts` (KD-13 selector set for `__mnemeDevSnapshot__`). Entire forwarder gated by `import.meta.env.DEV`, stripped from production builds.
- **D-SF-02 Eight signal classes**, all writing through three Tauri commands (`dev_log_console_entry` / `dev_log_network_entry` / `dev_log_perf_entry`) into three log files (`.dev-logs/console.log`, `.dev-logs/network.log`, `.dev-logs/perf.log`):
  - `console.log/info/debug/warn/error` (5 levels, monkey-patched with original-reference closure preservation)
  - `window.onerror` (tag `uncaught`)
  - `window.onunhandledrejection` (tag `unhandled-rejection`)
  - Resource load failures (`window.addEventListener('error', h, true)`, tag `resource-error`)
  - CSP violations (`securitypolicyviolation` event, tag `csp`)
  - `fetch` global wrap (method/url/status/duration)
  - `XMLHttpRequest.prototype.open + send` monkey-patch
  - `PerformanceObserver` for `largest-contentful-paint` / `paint` / `layout-shift` / `longtask`
- **D-SF-03 Rust-side debouncing + rotation:** 100 ms batched writer per file (`tokio::sync::mpsc` + dedicated writer task), rotate at 10 MB to `<file>.log.1` (overwriting single backup), `OpenOptions::new().append(true).create(true)`.
- **D-SF-04 `.catch(() => {})` around every invoke** in forwarder so log-write failures never crash the forwarder.
- **D-SF-05 Production-build verification:** grep `dist/` post-build for `installConsoleForwarder` / `__mnemeDevSnapshot__` / `[FRONTEND_CONSOLE]` / `[FRONTEND_NETWORK]` / `[FRONTEND_PERF]` — all must be absent.

  2. Custom dev-only binary `src-tauri/src/bin/dev_invoke.rs` exposing the commands in a minimal Tauri runtime context.
  3. `node -e` calling Tauri JS API.

- **D-UP-01 Three patches to `~/.claude/get-shit-done/workflows/verify-work.md`:**

## Specific Ideas

### Bootstrapping execution order (constraint from `design.md` Migration Plan)

GSD upstream groups (5 + 6 + 7) MUST land before mneme-side groups (1 + 2 + 3 + 4). Reason: `/gsd-verify-work 01.1` runs against the patched workflow, on the very phase that patched it. If upstream patches don't exist yet when verify-work fires, the workflow can't self-validate.

The GSD planner's task graph MUST reflect this: upstream-touching plans (PLAN-files mapping to OpenSpec tasks groups 5, 6, 7) go in the early waves; mneme-side plans (tasks groups 1, 2, 3, 4) follow; group 8 (deps + CLAUDE.md) + 9 (dogfood) + 10 (wrap-up) close out.

### TDD ordering heuristic (from `references/tdd.md` + `--tdd` flag)

`--tdd` mode applies `type: tdd` to eligible tasks. The eligible-task heuristic (per `references/tdd.md`):

- **High TDD value:** SDK handlers (group 6), npm-script bridge (group 4), `verify.validate-html` (group 6.8), `verify.parse-review-response` (group 6.7), forwarder log shape contracts (group 2 scenario tests), Rust command CLI invocation (group 3.0 spike outcomes).
- **Low TDD value:** workflow `.md` patches (group 5 — markdown, no executable assertion), HTML template (group 7 — visual artifact, validated structurally by `verify.validate-html` not by unit test), `.dev-logs/` scaffold (group 1 — directory + README), dogfood task (group 9 — full-stack integration, validated by `/gsd-verify-work 01.1` itself).
- **TDD via scenario test:** the OpenSpec `spec.md` already lists ~30 scenarios. Many can become integration / unit tests directly (e.g., "Failed fetch captured → `.dev-logs/network.log` contains line of shape X"). Planner should map each TDD-eligible task to its OpenSpec scenario.

### Atomic-commit boundaries

Planner should split atomic commits so each commit is independently revertable:

- `.dev-logs/` scaffold + `.gitignore` entry → one commit
- Svelte forwarder + its scenario tests → one commit (or split per signal class if file size pushes 800-line limit)
- Each of the 5 Tauri Rust commands + tests → atomic per-command (3 log handlers can batch together since they share the writer task)
- npm scripts → one commit per script + smoke test
- Each upstream workflow patch → independent commit (so `git revert` of any single patch is clean — but note upstream history is separate from mneme history)
- Each SDK handler → one commit per handler + smoke test
- HTML template → one commit
- Dependencies registry + CLAUDE.md pointer → one commit
- Dogfood findings → one commit
- Wrap-up (openspec validate, audit notes) → one commit

### Anti-pattern guards (memory-recall — applied this phase)

- **Memory `feedback_gsd_validate_commit_heredoc.md`:** GSD validate-commit hook doesn't parse heredoc commit messages. **Apply:** all commit messages in execute-phase use multiple `-m` flags, NOT `git commit -m "$(cat <<EOF...EOF)"`.
- **Memory `feedback_prototype_html_playwright_verify.md`:** prototype HTML as visual SSOT requires playwright screenshot verification, not code-level diff. **Apply:** Phase 01.1's dogfood validation (group 9) MUST verify the HTML template renders correctly by rendering it once and screenshot-comparing, NOT by inspecting tag presence.
- **Memory `feedback_long_lists_to_html.md`:** chat ≤ 3 messages; long lists → HTML aside. **Apply:** planner's PLAN.md files are durable .md (the long-form SSOT); any user-facing summary message at end of plan-phase stays terse.
