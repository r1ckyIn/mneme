# Phase 01.1 Learnings: dev-feedback-loop-infrastructure

## Decisions

### D-UP-01/D-UP-02 — 3-patch + .bak strategy for GSD upstream `verify-work.md`
Patched `$HOME/.claude/get-shit-done/workflows/verify-work.md` with three discrete patches (top-level `<critical_rules>` block, new `<step name="package_manual_review">`, Tauri-shell branch in `automated_ui_verification`) and preserved a `.bak` rollback snapshot.

**Rationale:** Patches are surgical (adding rule layer + step + IF branch) rather than rewriting; the `.bak` enables clean rollback if upstream PR cycle has issues. Keeps the change reviewable hunk-by-hunk for the eventual `gsd-build/get-shit-done` upstream PR.
**Source:** 01.1-CONTEXT.md (D-UP-01, D-UP-02), 01.1-02-SUMMARY.md

### E1 errata — `screencapture -l/-R` instead of `WebviewWindow::capture()`
Tauri 2's `WebviewWindow::capture()` doesn't actually exist as a stable cross-platform API; macOS-specific `screencapture` subprocess is the ONLY validated path for window/webview screenshots. CGWindowID resolved via `objc2-app-kit NSWindow.windowNumber()`.

**Rationale:** Discovered during phase research (RESEARCH.md E1) that v3 design's assumption was wrong. `screencapture -l <CGWindowID>` (webview) and `screencapture -R <x,y,w,h>` (window) work reliably and don't require additional Rust dependencies.
**Source:** 01.1-RESEARCH.md (E1), 01.1-06-PLAN.md errata_honored, 01.1-06-SUMMARY.md

### E2 errata — `dev_invoke` as Cargo `[[bin]] required-features = ['dev-invoke']`
There is no `tauri invoke` CLI; the executor pattern requires a custom Cargo binary `src-tauri/src/bin/dev_invoke.rs` gated by feature flag.

**Rationale:** v3 design assumed a `tauri invoke` CLI that doesn't exist. Custom `[[bin]]` with `required-features` keeps dev_invoke off the default build path (release-binary clean).
**Source:** 01.1-RESEARCH.md (E2), 01.1-06-PLAN.md, 01.1-06-SUMMARY.md

### E3 errata — TS+CJS dual-surface mirror for SDK handlers
8 SDK handlers exist on TWO surfaces kept in sync: TS npm package `@gsd-build/sdk` (`verify-dev-loop.ts` + `command-manifest.verify.ts` + `index.ts`) AND CJS shim router (`verify-dev-loop.cjs` + `verify-command-router.cjs` + `command-aliases.generated.cjs`). Single new file with 8 exports per surface (NOT "8 separate files" as v3 design assumed).

**Rationale:** SDK is an installed npm package, not a file-drop directory. Allow-list registration via `command-manifest.verify.ts`. CJS shim mirrors so non-TS-aware tooling still resolves the handlers.
**Source:** 01.1-RESEARCH.md (E3), 01.1-04-SUMMARY.md

### E4 errata — port 5173 strict, fail loud (no fallback to 1421)
`verify.start-dev-loop` uses Vite's strictPort behavior: on `lsof :5173` hit, returns `{error: "port 5173 in use", existing_pid: <N>, hint: ...}` and exits — never falls back to 1421.

**Rationale:** Silent fallback hides legitimate errors (user's existing dev shell, stale process). Fail-loud forces conscious cleanup. existing_pid lets the caller decide whether to kill or reuse.
**Source:** 01.1-RESEARCH.md (E4), 01.1-04-SUMMARY.md

### E5 errata — `src-tauri/src/dev.rs` parallel to `session.rs` (not `commands/` subdir)
Followed existing mneme codebase convention (session.rs at top-level) instead of v3's hypothetical `commands/` subdir.

**Rationale:** Mirroring established structure improves grep-discoverability and matches reader expectations for new modules in this codebase.
**Source:** 01.1-RESEARCH.md (E5), 01.1-PATTERNS.md, 01.1-06-SUMMARY.md

### E6 errata — per-PerformanceObserver-type try/catch for Safari 16
`PerformanceObserver.observe({type: 'X'})` calls each wrapped in try/catch because macOS 13.4 WKWebView (Safari 16) doesn't support `largest-contentful-paint` entry type. Unsupported types skip silently with one-time `[forwarder] LCP unavailable` info log; corresponding field falls back to `null` in `__mnemeDevSnapshot__`.

**Rationale:** Safari 16's PerformanceObserver throws on unsupported types — without try/catch, one missing entry type would crash the whole forwarder. Fallback to null preserves snapshot shape for downstream consumers.
**Source:** 01.1-RESEARCH.md (E6), 01.1-05-SUMMARY.md

## Lessons

### F1 — `verify.validate-html` regex parses HTML comments as live DOM
Validator's `<section\b[^>]*\bdata-bucket=` regex matches against raw file content including content inside `<!-- ... -->`. Cycle-1 template had a doc comment listing forbidden bucket values literally as `<section data-bucket="hybrid">` examples — validator counted them as live DOM and rejected the rendered output.

**Context:** Surfaced during cycle-1 dogfood. Auto-mode classifier blocked self-modification of `verify-dev-loop.cjs` to fix in-flight (correct per D-DF-03). Mitigated cycle-2 by removing `<section data-bucket=` literal from template's doc block (prose listing instead). Underlying SDK regex bug remains for future templates using example-DOM-in-comment docs — tracked in upstream-pr followup.
**Source:** 01.1-09-SUMMARY.md, dev-feedback-loop-audit-202605.md (F1), 01.1-REVIEW.md cycle-2 mitigation note

### HG-01/HG-02 surfaced because gsd-dev-* mjs scripts had no test coverage
Code-review found 1-line regex bug in `gsd-dev-snapshot.mjs:105` (regex required `\s*$` after `}` but actual format had `|` terminator — never matches). Verifier's structural check passed because it didn't run the script end-to-end. Fix pass added `scripts/__tests__/gsd-dev-snapshot.test.mjs` (5 scenarios + HG-01 regression) — WR-03 meta finding closes the gap.

**Context:** Verifier (R1-R9 contract) and code-reviewer found different things. Verifier checks "does deliverable exist + match spec shape"; code-reviewer checks "would this actually work at runtime". Both needed, neither sufficient alone.
**Source:** 01.1-REVIEW.md (HG-01, WR-03), commits `cba2312` + `6378f15`

### R9 Approach A unsatisfiable in Tauri 2.11.1
User-defined `#[tauri::command]` functions do NOT accept `allow-*` permission entries — Tauri 2.11.1 only resolves permissions from plugin manifests. Plan 01.1-06 envisioned auto-registering 5 dev-only permissions via `gen-capabilities.ts`; the spread is now commented out with a 30-line rationale block; `DEV_ONLY_PERMISSIONS` array preserved as documentation.

**Context:** Discovered during plan 01.1-06 execution. Rule 1 deviation auto-fix. The capability auto-generation flow doesn't fully work as the plan envisioned, but the dev commands still register correctly via `tauri::generate_handler!` (just without the formal capability allow-list).
**Source:** 01.1-06-SUMMARY.md (Deviations §1)

Plan task "verify CLAUDE.md added a `## Patterns` row" deliberately FAILED its `git diff HEAD~1 HEAD --stat | grep CLAUDE.md` check. Agent applied at filesystem level to BOTH worktree AND main repo so the pointer survives worktree deletion + grep still works after.

**Context:** r1ckyIn L2 rule "CLAUDE.md 绝不推送到 GitHub" + `.gitignore:40` exclude. Plan didn't anticipate this collision.

### Dogfood cycle 1 produced scope-changing UX feedback (Living adoption)
Cycle-1 user reply was NOT a simple approve/reject — it was a complete replacement visual contract (12K char Living spec) injected mid-checkpoint. The plan didn't anticipate this, but D-DF-03 audit-notes contract correctly handled it: record finding, propose path forward (in cycle 2: orchestrator rewrote template inline), don't auto-extend phase scope without user authorization.

**Source:** 01.1-09-SUMMARY.md (cycle 2 section), dev-feedback-loop-audit-202605.md (F4)

### Workflow's automated `cold-start` smoke test injection is wrong fit for infrastructure phases
The verify-work workflow's `extract_tests` step auto-injects a "Cold Start Smoke Test" when SUMMARY.md files modify paths matching `index.ts` / `lib.rs` / etc. For Phase 01.1 (which only added `mod dev;` behind `cfg(debug_assertions)`), production cold-start is unchanged from Phase 1 — the injection is pattern-match noise. User explicitly called this out: "这不属于四桶任务中的类别".

**Context:** The 4-bucket Visual Review model + cold-start auto-injection are both designed for phases that produce user-observable runtime behavior. Pure-infrastructure phases need a different verification path (auto-verified UAT with no conversational present_test).
**Source:** /gsd-verify-work 01.1 user feedback during this session, 01.1-UAT.md (Items NOT verified)

### Probe wiring intent mismatch — "is dev shell up?" vs "is project capable?"
`npm run gsd-dev-screenshot --silent --dry-run` exits 0 ONLY if `.dev-logs/dev-server.pid` exists. Workflow uses this as TAURI_CAPABLE detection — but the probe answers "is dev shell currently running" not "is this project capable of Tauri verify". Catch-22: the workflow's intent might have been "auto-start dev shell if capable", but probe semantics force "user must pre-start" model.

**Context:** Surfaced during today's `/gsd-verify-work 01.1` invocation. TAURI_CAPABLE=0 because user didn't pre-start `npm run tauri dev`. Probe behavior is by design per script comments, but the design choice is debatable for batched verify flows.
**Source:** scripts/gsd-dev-screenshot.mjs lines 52-65, /gsd-verify-work 01.1 invocation today

### Husky pre-commit running tests blocks RED-only TDD commits
Plans 01.1-05 and 01.1-07 documented Rule 3 deviations: tried to commit a RED-only failing test, husky's `npm test` pre-commit hook ran the failing test and blocked the commit. Workaround: rebalance commit boundaries so RED test ships in same atomic commit as GREEN implementation.

**Context:** Tension between TDD discipline (RED → GREEN as separate commits) and CI-style pre-commit hooks. The pre-commit hook treats ALL test runs as ship gates, not as "tests that should fail in TDD's RED phase". Solution: commit-boundary rebalance per plan-by-plan judgment.
**Source:** 01.1-05-SUMMARY.md (Deviations §1), 01.1-07-SUMMARY.md (Deviations §3)

## Patterns

### 4-bucket Visual Review HTML (visual / window / motion / perf)
Batched human-judgment surface organized into 4 fixed buckets enforced by `verify.validate-html`. Each bucket section gets editorial skeleton (num + num__label + title + caption) + concrete-anchored questions (screenshot / GIF / selector / locked-token comparison). User receives ONE HTML path and replies once.

**When to use:** ANY phase with user-judgment-needed UI surface. Replaces conversational one-test-at-a-time present_test loop. Skip when no UI surface (infrastructure phases — see Phase 01.1).
**Source:** 01.1-CONTEXT.md (D-UP-01 patch 2 + D11), 01.1-03-SUMMARY.md, .planning/references/design/living-visual-contract.md

### E3 dual-surface mirror — TS npm package + CJS shim router
For SDK handlers that need to be callable from BOTH the modern TS surface (typed clients) AND the legacy CJS shim (older tooling), mirror the implementation across two surfaces with allow-list registration on each.

**When to use:** Any new SDK command that needs to work with mixed-runtime tooling. Mneme's `@gsd-build/sdk` + `~/.claude/get-shit-done/bin/lib/` was already the canonical example.
**Source:** 01.1-RESEARCH.md (E3), 01.1-04-SUMMARY.md

### Out-of-repo file changes documented in SUMMARY with SHA-256 hashes
Plans 01.1-02 / 03 / 04 modified files in `$HOME/.claude/get-shit-done/` and `$HOME/.npm-global/` — outside the git tree. Each SUMMARY.md embedded full diff verbatim + SHA-256 hash + final line count for the upstream PR draft to consume later. The in-repo commit contained mostly SUMMARY.md + minimal in-repo metadata.

**When to use:** Any GSD upstream patch / cross-repo modification work. Treats SUMMARY.md as the audit trail for changes that git can't track in this repo.
**Source:** 01.1-02-SUMMARY.md, 01.1-03-SUMMARY.md, 01.1-04-SUMMARY.md

### Editorial skeleton (num + num__label + title + caption) per section in Living
Every section starts with: mono editing num (e.g., "01") + sans uppercase eyebrow with 1.4rem horizontal line prefix + Fraunces serif title with `<em>italic olive accent</em>` + Fraunces light caption max-width 42ch. Reusable structure across visual/window/motion/perf sections.

**When to use:** Any HTML generation under Living visual contract. The "Living 视觉规范" SSOT documents this as section 8 "编辑骨架".
**Source:** .planning/references/design/living-visual-contract.md (Ch 8), 01.1-09-SUMMARY.md cycle-2 rewrite

### Worktree-isolated parallel execution + post-wave merge
Plans within a wave run in `isolation="worktree"` parallel processes; orchestrator merges branches back after wave completes; `.gitignore`-protected `STATE.md` / `ROADMAP.md` get backed-up + restored to prevent last-merge-wins overwrites. Sequential dispatch (run_in_background:true, one Task at a time) avoids `git worktree add` lock contention.

**When to use:** Multi-plan waves with non-overlapping `files_modified`. Plans that touch shared orchestrator-owned files must use sequential mode (no worktree).
**Source:** 01.1-CONTEXT.md (multiple plans), execute-phase workflow (steps 5.5/5.7), Plan 01.1-10 chose sequential mode for STATE.md write

### Soft-error JSON envelope for SDK / CLI handlers
Every dev-feedback-loop handler that can fail returns `{error: "...", hint: "..."}` JSON to stderr + non-zero exit. Workflow callers parse stdout JSON instead of relying on exit codes. Examples: D-BR-02 envelope (npm scripts), `verify.scan-signals` when no dev server, `verify.validate-html` when forbidden_bucket.

**When to use:** Any handler in a batched/automated workflow where partial failure should not abort the entire flow. Caller can inspect the structured error and decide.
**Source:** 01.1-04-SUMMARY.md (D-PR-04), scripts/gsd-dev-*.mjs files (D-BR-02), 01.1-09-SUMMARY.md (Tauri-shell soft-error path verified)

### Code-review fix pass within current phase (vs new gap-closure phase)
Post-execute code-review found 2 HIGH + 4 MEDIUM + 3 LOW. Two paths considered: open Phase 01.2 gap-closure plan, or run gsd-code-fixer agent inside the current phase. ## Surprises

### Tauri 2.11.1 `#[tauri::command]` capability registration limitation
Plan 01.1-06's R9 Approach A (auto-register dev-only permissions via `gen-capabilities.ts`) turned out to be unsatisfiable: Tauri only resolves `allow-*` from plugin manifests, not user-defined commands. Documented in code with 30-line rationale block; commands still work via `tauri::generate_handler!`, just without formal capability allow-list.

**Impact:** Plan 06 ships a documentation gap (DEV_ONLY_PERMISSIONS array preserved as docs only) + the spread is commented out. Future Tauri version might unlock this; for now, capability gating relies on `cfg(debug_assertions)` alone.
**Source:** 01.1-06-SUMMARY.md (Deviations §1)

### `gh pr merge --delete-branch` auto-handles local feature branch cleanup
After merging PR #1, the gh CLI automatically: (1) deleted remote branch, (2) checked out local main, (3) fast-forwarded local main from feature-branch HEAD to merge commit, (4) deleted local feature branch. Manual cleanup steps in my "合并后建议" were unnecessary — gh did them all.

**Impact:** Saved 3-4 manual commands. Worth knowing for future PR merges; default `gh pr merge` flow is more complete than the workflow's documented post-merge steps suggest.
**Source:** /gsd-ship 01.1 invocation, gh pr merge output

### User cycle-1 reply was 12K-char visual spec drop, not approve/reject

User instead injected the complete "Living" visual contract as the new visual hard contract for HTML generation. Required mid-checkpoint scope renegotiation (orchestrator handled by rewriting template + saving SSOT + cycling back to user with new screenshot).

**Impact:** Cycle 2 added ~2 hours of work (template rewrite + SSOT MD + audit append + re-render). User got the visual identity they wanted; project gained Living visual contract SSOT. The mid-flow scope expansion was valuable, not noise.
**Source:** 01.1-09-SUMMARY.md cycle 2 section, dev-feedback-loop-audit-202605.md (F4)

### `verify.validate-html` regex matched HTML comments as live DOM
The validator's `<section data-bucket=` regex didn't strip `<!-- -->` comments before matching. The KD-13 template's top doc block listed forbidden bucket values literally as `<section data-bucket="hybrid">` examples — validator counted them as live DOM and rejected the rendered output entirely.

**Impact:** Cycle 1 dogfood couldn't validate the rendered HTML at all. Mitigated cycle 2 by removing `<section data-bucket=` literal from template's doc block. Underlying SDK regex bug remains; tracked in upstream-pr followup as nice-to-have (demoted from blocking).
**Source:** 01.1-09-SUMMARY.md (F1), dev-feedback-loop-audit-202605.md (F1 + cycle-2 mitigation)

### Verifier (PASS 9/9) and code-reviewer (2 HIGH + 4 MED) found different things
Verifier said R1-R9 spec contract met. Code-reviewer found HG-01 (regex never matches) + HG-02 (orphan file protocol). Both reports were correct — they checked different layers. Verifier checks "deliverable exists + matches spec shape"; code-reviewer checks "would this actually work at runtime".

**Impact:** Reinforces that BOTH gates are needed, neither sufficient alone. Saved the project from shipping `npm run gsd-dev-snapshot` with a regex that always timed out.
**Source:** 01.1-VERIFICATION.md, 01.1-REVIEW.md

### `branching_strategy: none` left 180 commits on local main, 133 unpushed pre-01.1
Phase 01.1 was inserted with `branching_strategy: none` and committed directly to local main. Combined with Phase 0 + Phase 1's prior unpushed work, local main was 180 commits ahead of origin/main. `/gsd-pr-branch main` exited as no-op (we're ON main, AHEAD=0 of target=main). Resolved by creating bundled feature branch + big PR for all 180 commits (option B).

**Impact:** Surfaced a workflow gap: solo-dev `branching_strategy: none` over multiple phases without intermediate ship breaks the "1 phase = 1 PR" invariant. PR #1 ended up bundling Phase 0 + 1 + 1.1, which is fine for solo-dev but loses per-phase PR audit trail. Future: either ship-per-phase (use phase branching) or accept bundled ship boundaries.
**Source:** /gsd-pr-branch main + /gsd-ship 01.1 session diagnosis, PR #1 description
