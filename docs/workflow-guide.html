1. 为什么要三层？

单层 GSD 已经搞定了 80% 的工作。三层不是推翻它，是补两个 GSD 不擅长的角落。

GSD 是「流程编排」——它告诉你做事的顺序（discuss → plan → execute → ship），但有两个地方它做得轻：

  • 规格沉淀：phase 1 决定了 X，phase 8 还能找到当时为什么这么决定吗？GSD 的 PHASE-N-PLAN.md 各管各，没有"跨 phase 长期规格"的概念。OpenSpec 补这个。
  • 底层硬约束：CLAUDE.md 是"软建议"（提示词），Agent 大概率遵守但有时偷偷违规。需要 hook 级别强约束 + 静态扫描。ECC 补这个。

把项目想象成做菜：

  • GSD = 菜谱（先切菜，再热油，再下锅，最后调味）。你需要的是动作顺序。
  • OpenSpec = 你家厨房的历代记录本（"上次用这个酱油咸了，下次少放半勺"）。跨多次做菜的记忆。
  • ECC = 厨房安全设施（油烟报警器、防滑垫、灭火器）。你日常感觉不到，但出事时救命。

三层都装好之后，你做的事 95% 还是 GSD，只是新增几个时机用 OpenSpec 沉淀决策。ECC 你基本不会主动调用——它装好了就在那。

2. 每一层到底干啥

Layer 1
GSD
流程编排 · phase 生命周期 · 你已经在用 · /gsd-*
Layer 2
OpenSpec
跨 phase 规格沉淀 · 提案 → 应用 → 归档生命周期 · /opsx:*
Layer 3
ECC
基础设施（rules / agents / hooks / skills）· 跨项目共享 · 大部分无形

每层都装在哪？

层装在哪影响范围
GSD~/.claude/get-shit-done/ + ~/.claude/agents/gsd-*用户级（所有项目）
OpenSpecMneme/openspec/ + Mneme/.claude/commands/opsx/项目级（仅 Mneme）
ECC~/.claude/{rules,skills,agents,commands}/ecc/用户级（所有项目）
AgentShield全局 npm CLI（只装了 CLI，没装 runtime）按需手动跑
关键：命名空间隔离

三层互不踩脚，因为：

  • GSD 用 gsd-* 前缀（agent 文件、hook 文件、slash 命令都是）
  • OpenSpec 用 /opsx:* 前缀 + 项目内 openspec/ 目录
  • ECC 装在自己的 ecc/ 子目录里（rules/ecc/、skills/ecc/ 等）

所以 ECC 的 50 个 agent + 148 个 skill 加进来，你的 33 个 gsd-* agent 一个都没被覆盖。已用 diff 验证过零文件冲突。

3. OpenSpec 深入：propose → apply → archive

这是你新增的工作内容。如果只能记住一件事——记这个三段式生命周期。

它解决什么问题？

假设这种情况：phase 3 你决定用 agentmemory 做知识图谱（因为 Apache-2.0 + SQLite + Obsidian export 三个条件都满足）。到了 phase 7 实施时，你忘了为什么不选 Cognee。翻 PHASE-3-PLAN.md 翻得头疼，找不到那段评估。

OpenSpec 让你在 phase 3 决定时，开一个 proposal，把"为什么选这个、否决了哪些"写成结构化文档，phase 3 ship 时归档进 openspec/specs/memory-engine.md。到了 phase 7，cat openspec/specs/memory-engine.md 就看到完整决策史。

三个动作

① /opsx:propose <feature>

意思："我要做一个变更，先讨论清楚要做什么"。Claude 会创建 openspec/changes/<feature>/ 目录，包含四个文件：

openspec/changes/add-dark-mode/
├── proposal.md   # 为什么做、不做什么
├── specs/        # 这个变更影响哪些 spec
├── design.md     # 技术方案
└── tasks.md      # 具体任务清单

这个时候还没改任何代码。proposal 是"我们打算这么干，对不对"。

② /opsx:apply <proposal-id>

意思："上面那个 proposal 通过了，现在 Claude 按 tasks.md 一项项实现"。

Apply 阶段 Claude 会跟着 tasks.md 的 checklist 改代码、跑测试、commit。本质上是 OpenSpec 自带的 mini 执行器（你用 GSD 时主要用 /gsd-execute-phase 跑这一步，apply 是辅助、不强制）。

和 GSD 的关系

不用都用。在 Mneme 试点里，实际跑代码用 /gsd-execute-phase（你熟），apply 只用来标记"proposal 已经动手了"的状态切换。Apply 的代码执行能力是 OpenSpec 的可选项，不是强制。

③ /opsx:archive <proposal-id>

意思："这个变更完成了，把它从 changes/ 归档进 specs/，成为长期规格"。

# Before archive:
openspec/changes/add-dark-mode/

# After archive:
openspec/changes/archive/2026-05-15-add-dark-mode/   # 时间戳标记的历史
openspec/specs/ui-theming.md                         # 长期 spec 更新

归档后 openspec/specs/ 里就有了这个能力的当前规格。下次有人（或你 4 个月后）问"我们的主题切换是怎么工作的"，cat 一下 specs/ 就答得出。

什么时候开 proposal？

问 1：这个变更跨多少 phase 还活着？
如果改完就忘（比如修一个 typo）→ 不开 proposal，用 /gsd-quick 就好
如果是会被未来引用的能力决策（"我们用 ts-fsrs 不用 fsrs-rs"）→ 开 proposal
问 2：这个变更的"为什么"重要吗？
如果不重要（按惯例做）→ 不开
如果重要（评估了多个备选）→ 开
问 3：这是 phase 内的实现细节吗？
是 → 写在 PHASE-N-PLAN.md，不开 proposal
否（跨越 phase 边界的能力）→ 开 proposal

Mneme 实例预判：phase 5.5 评估四个 KG library（Cognee / Zep+Graphiti / Mem0 / agentmemory）的决策 → 典型应该开 proposal。原因：跨 phase（影响 phase 7+）、有评估过程、未来你会反复 reference。

4. ECC 深入：你大部分时间感觉不到它在

ECC 不是命令集，是基础设施。装好就在那，不调用、不维护。

它装了什么？

东西数量实际作用
rules/ecc/16 种语言各语言通用规则，Claude 在写对应语言时会拉这些进上下文
skills/ecc/148 个各种工具技能（security-scan、research-first、tdd-guide 等）按需触发
agents/新增 50 个子 agent（如 code-architect、a11y-architect），Claude 自动调用
commands/新增 66 个新 slash 命令（如 /security-scan、/harness-audit）

ECC 像是给你的 ~/.claude/ 装了一个「工具箱大礼包」。你之前 ~/.claude/ 里只有 GSD 的 33 把工具，现在变成 83 把。Claude 决定什么时候用哪把，你不用挑。

你需要"主动用"的 ECC 部分

大部分 ECC 是 passive 的，但有几个 slash 命令你可能会想主动调用：

命令什么时候用
/security-scan大改之前或上线之前跑一次，AgentShield 扫整个 ~/.claude/
/harness-audit感觉工作流有点乱，跑一次诊断
/code-reviewECC 自带的，比 GSD 的更倾向语言特定规则；GSD /gsd-code-review 仍是主力

AgentShield CLI（不是 runtime）

AgentShield 是 ECC 生态里的安全审计工具。我们装了 CLI，没装 runtime monitor。区别：

  • CLI 模式（已装）：手动跑 agentshield scan --path ~/.claude，输出报告。静态扫描，对你工作流没干预。
  • Runtime mode（未装）：注册 PreToolUse hook，每次 Claude 调用工具都被拦截一下。动态拦截，可能跟 GSD 已有的几个 hook 打架。

所以现在的安全审计模式是：大节点（phase ship 前、重大改动前）手动跑一次 scan，看 grade 和 critical findings。日常开发不被拦截。

关于"什么时候装 runtime"，看 第 8 节。

5. 一个完整 phase 怎么走（11 步）

基于你熟悉的 GSD 流程，标红的是新增 OpenSpec 步骤，其他原封不动。

  1. 模糊需求 → SPEC.md /gsd-spec-phase N 你已熟悉。把 phase 的 WHAT 想清楚。
  2. 开 OpenSpec proposal /opsx:propose "phase-N-<feature>" 新 只对"跨 phase 重要决策"开 proposal。phase 内小修补跳过此步。
  3. discuss 阶段：assumptions 分析 /gsd-discuss-phase N --analyze 你已熟悉。挖 phase 隐含假设。
  4. plan 阶段：生成 PHASE-N-PLAN.md /gsd-plan-phase N [--tdd] 你已熟悉。Mneme 的业务逻辑 phase 建议加 --tdd。
  5. execute：跑 plan 里的任务 /gsd-execute-phase N 你已熟悉。波次并行执行 plan 任务。
  6. 代码审查 + 自动修复 /gsd-code-review N --fix --auto 你已熟悉。可选追加 /security-scan（ECC）做安全审计。
  7. UAT 验证 /gsd-verify-work N 你已熟悉。对话式验收。
  8. apply OpenSpec proposal /opsx:apply <proposal-id> 新 标记 proposal 已实施。如果第 2 步没开 proposal，跳过此步。
  9. 建 PR + ship /gsd-pr-branch main && /gsd-ship N 你已熟悉。过滤 .planning/ commit + ship。
  10. 提取学习 /gsd-extract-learnings N 你已熟悉。把 phase 决策、模式、惊喜写入 LEARNINGS.md。
  11. archive proposal → 写入长期规格 /opsx:archive <proposal-id> 新 把 proposal 沉淀进 openspec/specs/，未来跨 phase 可检索。
心智模型

原 GSD 流程 8 步（你已熟悉），加 3 个新步骤包夹起来：开头 propose、中间 apply（弱）、结尾 archive。如果 phase 没有跨 phase 决策，三个 opsx 步骤全部跳过——回到原来的 8 步 GSD。

6. 什么时候用哪个命令？

现在要做一个小改动（typo / 调样式 / 加一行 log）
→ /gsd-quick。不用 propose、不用 phase。
要开始一个新 phase
→ /gsd-spec-phase N 第一步。明确这个 phase 交付什么。
phase 内决策但跨多个 phase 还会被引用（如选 library、定 architecture）
→ /opsx:propose 在 discuss 之前开。结束时 /opsx:archive。
想知道某能力的当前规格（"我们的 KG 是怎么工作的？"）
→ openspec list --specs 看有哪些 spec，openspec show <name> 看内容。
大改之前想做安全审计
→ agentshield scan --path ~/.claude（在 shell 跑），或 /security-scan（ECC skill）
不确定一个变更要走哪条路径
→ /gsd-progress --do "我想..." 让 GSD 自动路由。
长期想法、跨 phase 的笔记
→ /gsd-capture --seed 或写 .planning/todos/pending/<date>-<slug>.md。
工作流卡死了不知道在哪一步
→ /gsd-progress 看当前状态，/gsd-forensics 深度诊断。

7. 常见坑

坑 1：proposal 开太频

容易把每个 phase 的每个小决定都开 proposal，结果 openspec/changes/ 堆满。正确做法：proposal 是"未来会引用"的决策。如果一个变更只在当前 phase 内有意义，写在 PHASE-N-PLAN.md 就行。

坑 2：proposal 开太大

把"整个 phase 7"开成一个 proposal，里面 50 个 task。正确做法：一个 proposal 对应一个能力（feature）。如果 phase 涉及多能力，开多个并行 proposal。

坑 3：忘了 archive

proposal 开了、做了，但 ship 时没跑 /opsx:archive。结果 openspec/specs/ 永远是空的，changes/ 堆着一堆已完成 proposal。正确做法：把 archive 当成 ship 的一部分（步骤 11），变肌肉记忆。

坑 4：以为 ECC 装了就要主动调

看到 ECC 有 148 个 skill 就想"我得搞清楚每个怎么用"。不需要。skill 是 Claude 按描述自动触发的，你不用记。日常你需要主动调的就是 /security-scan + /harness-audit（可选），其他时候它在后台。

坑 5：CLAUDE.md 改在 GSD 标记内被覆盖

Mneme/CLAUDE.md 有 <!-- GSD:workflow-start --> 等标记。这些标记内部的内容会被 GSD update 覆盖。要加自定义内容，放在标记之间（如 workflow-end 和 profile-start 之间的空白区）。

已经踩过的坑

本指南创建时，"Spec Layer (OpenSpec)" section 加在了 workflow-end 和 profile-start 之间——专门避开了 GSD 自动管理区。

坑 6：以为 AgentShield Grade D 是问题

初次跑 agentshield scan 可能看到 Grade D，吓一跳。看清楚：critical-only 模式下是 Grade A (95/100)。Grade D 来自 "85 个 unobserved skills" 这种 info-level 的标记问题，不是真实安全风险。

坑 7：上下文池容上当

装完三层一定要跑 /context 看实际占用。Mneme 实测 85.5K / 1M (9%)，非常健康。Skills 只占 18.3K（远低于"会爆"的担忧）。真正的大头是 Memory files（43.7K = CLAUDE.md 链）。

8. 关于 AgentShield runtime（后续决策）

这一节专门给你 phase-01 ship 完之后看。

为什么现在没装 runtime？

AgentShield runtime monitor 会注册 PreToolUse hook（每次 Claude 调用工具都被拦一下）。GSD 也有自己的 PreToolUse hooks（gsd-prompt-guard.js / gsd-read-guard.js / gsd-workflow-guard.js / guard-branch.sh）。

两个项目的 PreToolUse hook 同时存在的组合行为没人测过：

  • 会都跑一遍（双 tax 每次 tool call）？
  • 一个 short-circuit 另一个？
  • 顺序按文件名字典序决定，但语义冲突未知？

所以现在的策略是 CLI-only + 周期性手动扫描，确认 GSD 工作流在三层下健康运行后再决定。

什么时候 reactivate？

已经在 .planning/todos/pending/2026-05-11-post-phase-01-agentshield-runtime-decision.md 写好了完整决策清单。Phase-01 ship 后会通过 /gsd-capture --list 浮现。决策时三选一：

  1. 装 runtime（接受协同风险）
  2. 保持 CLI-only（推荐默认）+ 每个 phase plan 之前手动 scan 一次
  3. hybrid（runtime + ECC_HOOK_PROFILE=minimal 选择性 gate）

决策输入：phase-01 dogfood 期间有没有遇到 AgentShield 会拦的事故（secret 泄露 / 错配 wildcard permission / 误装恶意 skill）。如果没有任何 incident，强烈推荐 (2)。
