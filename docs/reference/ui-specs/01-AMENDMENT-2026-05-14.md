## Why this amendment exists

Phase 1 shipped 2026-05-13. The user then dogfooded the running app against the
Claude.ai web mental model and surfaced two related functional gaps:

1. **GAP-1 — Session lifecycle mismatch (REQ-02 acceptance gap).** Every prompt
   spawns a fresh `claude --print` subprocess via `buildClaudeArgs()` with NO
   `--resume`; Claude has zero memory of any prior prompt/reply pair in the same
   app-session. `setStatus("connecting")` fires only when the user sends a
   prompt — NOT at app boot. `setStatus("disconnected")` fires in `teardown()`
   on EVERY subprocess close (= after every response), so the titlebar dot
   blinks grey between prompts even though the app is alive. Claude.ai web's
   contract: app open → connected; sending prompts keeps connected; only app
   close → disconnected.

2. **GAP-2 — Output rendering doesn't match Claude.ai web (REQ-05 sanitize +
   visual hierarchy gap).** Claude responds to a math prompt with BOTH `$$...$$`
   AND a redundant ASCII fallback (e.g. `2!f''(a)(x-a)2`) on the next line —
   caused by Claude Code CLI's terminal-oriented default system prompt.
   Markdown headings render flat: h1/h2/h3 all share 16px / weight 600 /
   letter-spacing -0.005em in AssistantMessage.svelte L118-127. Even when
   Claude emits h1+h2+h3 hierarchically, the output reads as one giant flat
   blob. `<hr>` (`---` separators) renders invisible — no rule existed.

Root cause for GAP-2 is high-confidence: Claude.ai web hands Claude a CHAT-UI
system prompt ("client renders rich markdown + KaTeX, no ASCII fallback
needed"); mneme spawns `claude --print` which inherits the CLI's CODING-AGENT
system prompt. The output divergence is server-side prompt-driven, not
client-side render-driven.

This amendment closes the drift atomically across two paired plans:

- **Plan 01-12** (this code-layer plan) closes the drift with three deltas
  (A-16 session resume, A-17 mneme-rendering-hints, A-18 heading hierarchy +
  hr styling).
- **Plan 01-13** (wave 10, pure docs) propagates the contract changes into
  SPEC.md REQ-02/REQ-05 acceptance criteria + REQUIREMENTS.md traceability.
  Split per plan-checker H-3 so Plan 01-12 can revert cleanly if Task 4a Tauri
  multi-entry capability spike forces redesign.

## Delta inventory — three amendments

Each delta follows the structure: **What / Why / Source of truth / Impacted plans**.

### A-16 — Session resume via `--resume <session_id>` (REQ-02 acceptance gap closure; clarifies + supersedes A-10).

**What:** Every prompt after the first in an app-session passes `--resume` with
the session id captured from the first system/init event of the FRESH
`claude --print` subprocess. The captured id is threaded through
`buildClaudeArgs(prompt, scratch, { resumeSessionId: dispatch.sessionId,
appendSystemPrompt: CHAT_RENDERING_HINTS })`. The `connected` connection status
is held for the entire app lifetime once flipped, regardless of per-prompt
subprocess close events.

**Verbatim A-16-supersedes-A-10 clause (per plan-checker H-4 — DO NOT paraphrase):**

> A-16 (clarifies + supersedes A-10): The 'connected' status is held for the
> entire app lifetime once flipped, regardless of subprocess close events. Only
> app close (onDestroy / Cmd+Q PGID kill) OR spawn-or-register error flips back
> to 'disconnected'. The phrase 'auto-degrades to disconnected on subprocess
> exit error' in A-10 was incompletely implemented in plan 01-06 commit — the
> original intent was 'spawn-error path' (cmd.on('error') + spawn-or-register
> catch), NOT 'subprocess natural close path' (cmd.on('close')). Plan 01-12
> closes this implementation gap.

**Why:** Phase 1 dogfood revealed that without `--resume`, each prompt spawns
a fresh session and Claude has no memory of prior turns — fails the implicit
"single Claude chat session" mental model of REQ-02 acceptance. The
connection-state symptom (titlebar dot blinking grey between prompts) was the
visible artifact of the same underlying bug.

**Tauri 2 capability topology** (Task 4a spike outcome — Option B): the capability
JSON registers TWO Command names under `shell:allow-spawn` and
`shell:allow-execute`:

- `claude-bin-fresh` — 15-arg validator array (no `--resume`).
- `claude-bin-resume` — 17-arg validator array (with `--resume` +
  SESSION_ID_REGEX).

ChatPanel.sendPrompt selects the Command name based on `dispatch.sessionId`
presence. Tauri 2's `tauri-plugin-shell` scope-resolution uses
`scopes.iter().find(|s| s.name == command_name)` — short-circuit on first
matching name — so multiple `allow` entries with the SAME name silently shadow
each other (Option A — union semantics — IS impossible in upstream Tauri).
Distinct names avoid the multi-entry-with-same-name pitfall. See
`spike-tauri-capability-multi-entry.md` for the source-code-of-truth probe.

**Source:** dogfood 2026-05-14 user feedback. Impacted plans: 01-12 (code),
01-13 (docs).

### A-17 — Mneme-rendering hints via `--append-system-prompt <CHAT_RENDERING_HINTS>` (REQ-05 sanitize + UX gap closure).

**What:** Every prompt passes a fixed 280-character hints string
(`CHAT_RENDERING_HINTS` in spawn-args.shared.ts) telling Claude the client
renders KaTeX so it should not emit ASCII-fallback lines.

The hints literal is anchored byte-for-byte in the capability validator regex
via `escapeRegex(CHAT_RENDERING_HINTS)` so any drift between the SSOT literal
and the validator literal fails audit check 1 (SSOT drift) immediately. User
input cannot reach this position — the validator is `^<exact-literal>$`.

**Why:** dogfood revealed Claude Code CLI's default coding-agent prompt drives
terminal-friendly output (ASCII duplicate after math) that doesn't match
Claude.ai web's UX. The append flag is the narrowest possible surface — it
adds OUR rendering directive on top of the CLI's default; it does NOT replace
the default like `--system-prompt` would.

**Promotion path:** Phase 9 REQ-17 (per-course rules) replaces this fixed
string with `--system-prompt` full-replacement once per-course injection
lands. Phase 1 stays at append. Audit gate checks 4b + 9 (added by plan
01-12) reject the full-replacement flag at the validator AND SSOT layers
until Phase 9 explicitly opens the surface.

**Source:** dogfood 2026-05-14 + REQ-17 Phase 9 mapping. Impacted plans:
01-12 (code), 01-13 (docs).

### A-18 — Heading hierarchy + `<hr>` visual styling.

**What:** h1/h2/h3 differentiated CSS scale in
`src/lib/components/AssistantMessage.svelte`:

| Level | font-size | margin           | letter-spacing | line-height |
|-------|-----------|------------------|----------------|-------------|
| h1    | 21px      | 28px / 0 / 12px  | -0.012em       | 1.3         |
| h2    | 17.5px    | 22px / 0 / 10px  | -0.008em       | 1.35        |
| h3    | 15.5px    | 16px / 0 / 8px   | -0.005em       | 1.4         |

Plus `<hr>` rule: `border: 0; border-top: 1px solid var(--border-soft);
margin: 28px 0;` and an `h1:first-child { margin-top: 0; }` polish for
top-of-message headings.

**Why:** Prior combined rule rendered all three levels at 16px/600 with no
contrast; markdown hierarchy was visually invisible. Three font-size steps
(21 / 17.5 / 15.5) carry ≥2px scale contrast across adjacent levels, matching
Anthropic's serif hierarchy on Claude.ai web. `hr` was previously unstyled
(default browser inset 3D line doesn't match the Anthropic family).

**Source:** dogfood 2026-05-14 visual inspection. Impacted plans: 01-12
(code only — visual layer; 01-13 docs amendment does not touch this).
